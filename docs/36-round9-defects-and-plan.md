### 7.2 本批修掉的缺陷（8 个，全部先取 RED 见证）

| # | 缺陷（用户可见后果） | 根因 | 修法 |
|---|---|---|---|
| ㉜ | 慢供应商下几乎必失败：「AI 请求超时 / 计划请求超时」 | 传输超时预算（收 45s / 总 60s）是照 ~1s 延迟供应商定的；实测本供应商 TTFB 11s、整请求 40–55s | 收 45→**120s**、总 60s→**4 分钟**；新增「总上限 ≥ 会话流式上限」不变量 pin |
| ㉝ | 说「我忌口花生/我吃素」→ AI 回「已记下」，**其实什么都没写** | 本地修改意图判定缺「陈述式约束」，于是不催信封、散文+JSON 又被严格解析丢掉 | `_constraintPatterns`（第一人称约束 + 祈使句，排除第三方主语） |
| ㉞ | 「训练结束了，收工」→ AI 说「你还没有进行中的训练」 | 快照没有「进行中的训练」段，模型看不见活跃会话 | 快照新增该段（id + 已记组数 + 涉及动作） |
| ㉟ | 「把周一那个深蹲去掉」→ AI 要求用户去页面里读条目 id | 快照只给计划 id、不给条目 id，而命令要 `entryId` | 快照列出 `[pentry:…]`（每计划每天封顶 8 条 + 超量提示），并加别名与 hint |
| ㊱ | 「供应商返回格式无法识别。」（对话/计划/识餐三处都会） | 模型习惯「先写说明再贴 JSON / 包 ```json 围栏」 | 共享兜底 `salvageSingleJsonObject`（只认**恰好一个**顶层对象，有歧义就拒绝）；接进对话信封、计划、识餐三条出口 |
| ㊲ | 对话失败只写「发送失败，点击重试。」——**没有原因**（同一时刻设置页探针却写着真实原因） | 控制器把 `error.toString()` 塞进 state，气泡只取已生成分片（失败时为空） | 失败原因经 `safeFailureText` 白名单化后**进气泡**；原始异常不再上屏（更严） |

| ㊴ | **真照片发不出去**：一张 49 KB 的图就报「对话内容过长」 | 对话路径请求上限 64 KiB（按纯文字定的），照片 base64 后必然超 | 上限按「本条是否真带图」分档：文字仍 64 KiB，带图放到 **8 MiB**（与识餐出口同档） |
