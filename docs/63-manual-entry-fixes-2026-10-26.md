# 记录与目标的手动入口（2026-10-26 修复）

> 用户 2026-10-26 原话：「营养摄入自己不能改，运动记录也输入不了嘞，步数它读不到系统
> 数据，也不能自己输入」。
> 这一轮按这三条 + 顺着查到的同类问题施工：**先红后绿、变异验证、逐张实看实帧**。
> 实帧在 [`evidence/2026-10-26-edit-entry-fixes/frames/`](evidence/2026-10-26-edit-entry-fixes/frames/)，
> 门禁日志在同目录 `gate-logs/`。

## 0. 一句话结论

三条都不是崩溃，是「入口 / 能改的范围」问题：**运动记录与步数手动录入根本没有入口**，
**营养只能靠食物库推导**。本轮补齐 4 个入口（自由训练 / 自定义一顿 / 手动步数 /
手动营养目标），并顺手修掉 3 个真 bug（其中一个是「首读不写 0」被自己的开关流抵消）。

## 1. 三项修复（用户直接提的）

### 1.1 运动记录：自由训练入口（不依赖计划）

- **原来的阻断**：唯一路径是「计划 → 当天的计划日且有动作 → 开始训练」。**没有计划 =
  完全记不了训练**，今天不是计划日也记不了。
- **为什么好修**：数据层 `sessionRepository.start(planId: 可为 null)`、训练弹层（无计划
  时动作下拉直接列整个动作库，`_exerciseOptions`）、历史（显示「自由训练」）本来就全通，
  只差一个入口——这也是 AI 聊天 `session.start` 早就能做的事。
- **现在**：
  - 没有计划：空态里一枚「开始一次自由训练」（`training-start-free-empty`）；
  - 有计划但今天不是计划日：页面**中部**一行「今天不是计划日 · 开始一次自由训练」
    （`training-free-session`）；
  - 开成功后直接进训练弹层（记录一组 → 结束，行为与计划训练完全一致）。
- **判据**：点入口 → 库里出现 `planId = null` 的会话 + 弹层出现「训练进行中」；
  有「今天的计划日」时这枚入口**不出现**（不抢计划自己的开始按钮）。
- **变异验证**：把 `start()` 硬塞一个不存在的 planId → 断言红（`active` 为 null）→ 还原绿。

### 1.2 步数：不再用 0 冒充「没读到」+ 手动录入

- **原来的两个问题**
  1. 当天第一次读只是**立基线**（累计值就是基线），原来会落一行 `steps: 0`，卡上显示
     「0 / 10,000 步」——用户以为读数坏了；
  2. 完全没有手动录入，也没有补录。
- **现在**
  - 首次同步**只立基线、不落行**，卡上说「刚开始读取 · 走几步后点一下卡片刷新」；
  - 有数据时点卡 → 步数弹层：**「重新读取」**（真的同步一次）+ **「手动记录步数」**；
  - 手动值**当天优先**：`syncToday` 见到 `source = manual` 就不覆盖（用户的说法是事实，
    设备的「累计差」在换机/重启/多计时源时并不可靠）；卡上如实标一枚「手动」；
  - 「恢复自动读取」只清手动行，**不动传感器写的那一行**。
- **判据**：首读 `saved = false` + 库里没有行 + 卡上无「0」；手动记录后 `readDay.source =
  manual`、传感器同步 `manualKept = true` 且值不变；清掉后交还给传感器（差值照常落库）。
- **变异验证**：把「手动优先」与「首读不落行」两个分支同时关掉 → 3 条断言红 → 还原绿。

### 1.3 营养：可以自己填 / 自己定

- **「自定义一顿」**（记餐入口第三项）：不依赖食物库，直接填这一顿的热量与三宏量。
  数据层零迁移——`MealItems` 本来就允许 `foodId = null` + `sourceType = 'manual'` + 四个
  快照列。
- **手动营养目标**：热量卡脚注那一格（依据）现在**可点**，弹层里四行区间（热量/蛋白/碳水/
  脂肪，预填当前值），从**今天**起生效；同一弹层里可「恢复按身体数据计算」。
- **依据必须改口**：手动目标生效时，卡上写「手动设定的区间（不按公式）」——数字是用户填的，
  就不能再声称按 Mifflin–St Jeor 算。
- **判据**：保存后 `target.goalType = 'manual'` 且八个数字逐字相等；生效日在未来不套用；
  下限 > 上限被拒；卡上依据不含「Mifflin」；恢复后回到「没有目标」。
- **未做**：历史日期补记（记录页非今天只读是刻意设计，需要你点头才改）。

## 2. 顺手修掉的 4 个真 bug

1. **「首读不写 0」被自己的开关流抵消**（最隐蔽）：应用内开关监听的是 `app_settings`
   整张表，而步数**基线**也写在里面 ⇒ 首读写完基线又触发一次同步，第二次差值正好 0，
   照样落一行 0。改成**只在开关值真的变化时**才重读。
2. **手动步数弹层的 controller 在退场动画里被用**：原来 `whenComplete(dispose)`，弹层还在
   重建 `TextFormField` → 「A TextEditingController was used after being disposed」。
   改为弹层自己持有、自己 dispose。
3. **自由训练入口与右下浮钮重叠**：取帧实测页尾那一行被三枚浮钮压住（chevron 看不见），
   挪到页面中部（同时解释了「今天是休息日」）。
4. **热量卡新加的铅笔图标在 320dp × 2.0× 溢出 11px**：并排状态下「依据」那一格是被
   `Expanded` 挤出来的（只剩 ~9dp），14dp 图标必然撑破。改成**只有竖排（余量充足）才画
   图标**，两种状态都保留「整格可点」（`stress_ui_test` 实测抓到）。

## 6. 值得改进的几套方案（按「投入 / 收益」排序，供你挑）

### 方案 A：把「删除与修正」补齐（约半天）

**现状**：除了餐食、食物、记忆，其余记录只能增——饮水只能加不能删（仓库有
`water.delete`，**只有 AI 聊天能调**）、体重没有删除（只有同日覆盖）、菜品营养不能编辑、
训练会话与组次不能删/改。

**做什么**：给这四类各补一个「长按/菜单 → 删除（带确认）」+ 一处编辑；所有删除走
`AppSnackBar` 的撤销（仓库已有回写接口）。**为什么值得**：这是「记错了修不回来」，
比任何新功能都更常被用到。

### 方案 B：历史日期补记（约半天）

**现状**：记录页非今天**只读**（原设计是「历史回看面」）。**做什么**：允许补记近 N 天
（建议 30 天）的餐食/体重/训练，页面上明确标「补记」；未来日期仍然禁写（仓储已拦）。
**风险**：会改变「历史只读」这条既有设计口径，需要你点头。

### 方案 C：AI 与手动能力对等（约 1～2 天）

**现状**：37 条写入命令里有一批只有 AI 聊天能做（`water.delete`、`dish.upsert/update`、
`menu.snapshot.publish` 等），界面没有入口——用户不该为了删一条饮水去跟 AI 说话。

**做什么**：做一张「能力矩阵」测试（每个 `action` 必须标 `ui` / `ai-only` / `both`），
然后逐个补 UI 或显式标注；顺便让 AI 卡片上的「建议按钮」复用同一套入口。

### 方案 D：数据自检页（约 1 天）

**做什么**：设置里加「数据自检」：各表条数 + 最后写入时间 + 三类可修问题
（孤儿的 `mealItems.foodId`、`local_date` 格式异常、步数手动行残留），每类给一个
「修复」动作。**为什么值得**：今天这类「读了但显示不对」的问题（首读写 0）如果有自检，
用户自己就能看出来，不必等下一次反馈。

### 方案 E：空态与极端字号的统一清扫（约 1 天）

**做什么**：① 每个空态都给一个「现在能做的一件事」（今天的训练页空态就是这么修的）；
② 把所有页面按 320dp × 2.0× 扫一遍（这一轮在热量卡上又抓到一处 11px 溢出），
写成一份「极端字号清单」并加进门禁。

### 我的建议顺序

**A → C → D**：A 解决「修不回来」，C 解决「只有 AI 能做」，D 让这类问题以后能自查；
B 需要你先定口径；E 适合和 D 一起做（都要跑全页扫描）。
