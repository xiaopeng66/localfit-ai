# v4140 发布记录（2026-11-10 复核更正）

> **原说明有不准确的根因和过度承诺，以下按源码与失败回归更正。** 此处更正本地文档，不代表已发布的 v4140 APK 已包含后续源码修复。

## 原发布的意图与实际遗漏

v4140 原本试图让菜单页保留待分析供应，同时维持自动推荐的营养与份量门槛。但复核发现：

1. `MenuDishList` 仍订阅 `watchAnalyzable()`，待分析项在上游已被过滤；映射层的 `includePendingAnalysis: true` 无法把它们找回来。
2. 营养完整但每份重量未知的供应仍无法映射为可计算候选。**没有可计算候选不等于食堂目录为空**，原页面却混用了这两个状态。
3. 原映射用 `kcal=0` 占位待分析项，既不能解决上游过滤，也不应成为展示未知营养的方式。
4. AI「换一套」严格池要求完整营养及可信每份重量；历史估计份量不满足该门槛。候选池空时不会请求模型，原提示却统一称“AI 失败、已本地重排”，甚至在没有本地候选时也这样提示。

因此，原先“食堂 8 道菜都会显示、7 道进入推荐位”的说法没有端到端证据，**撤回该保证**。

## 归一补跑根因更正

原说明称归一器不支持“仅分析证据完整、供应未链接”，这是错误的：规则层和转换器原本就支持该形态。

本轮实际复现的是：供应**先登记为待补全，之后才补齐每 100g 证据**，已有台账把新证据误判为来源冲突；报告却仍按规则预判统计成功。另有重跑把冲突变成功并覆盖主库、补链接抹去用户明确份量来源的问题。

以上已建立真实 Drift 回归，修复后两份归一定向测试 **28/28**、营养契约/备份恢复/跨模块测试 **121/121** 通过。它们是后续源码验证结果，**不是 v4140 包的验证结论**。

## 证据边界与后续

- 用户截图表明“目录有 8 道、已分析 7 道”；本轮未取得用户手机数据库，不能据此断言每一行的 `food_id`、营养完整性或份量来源。
- 后续修复需分离“全量供应展示”和“可计算推荐池”，未知营养不填零、未知份量不补 100g，估计份量不自动变可信。
- 本轮源码修复与验证见 [跨链路回归证据](../evidence/2026-11-10-cross-flow-regressions/README.md)。当前没有因这次文档更正升版本、构建或发布新包。
