## 0. 结论摘要（v2 的五个关键修正）

1. **最大的质量收益不是向量模型，而是「菜品结构化标签 + 个人口味向量」。** 纯向量只能解决「说法不同」；
   而「清淡/辣/面/汤/油炸/主食」这类**意图**必须靠结构化标签 + 硬/软过滤，向量只做召回补充。
   因此本方案把「一次性给菜品打结构化标签（模型离线生成、用户可改）」列为 P1，与向量并列。
2. **融合不用手调权重，用 RRF（Reciprocal Rank Fusion）。** 向量分、关键词分、重要性、近期是四种量纲，
   加权和需要调参且易被单一信号支配；RRF 只看名次，`score = Σ 1/(60+rank_i)`，再叠加少量 boost。
3. **硬过滤只留安全与可用性，其余全部软惩罚。** 过敏/忌口、窗口营业中、菜品属于今日可用菜单 = 硬；
   「近 3 天吃过」「营养区间」「常去窗口」= 软（扣分而不是排除）——避免过滤把好结果杀光。
4. **性能分三档，不提前上重武器**：≤5 万条 int8 暴力余弦；>5 万条二值量化（Hamming）先筛 + int8 重排；
   >50 万条才上纯 Dart HNSW。P0 同时基准 int8 与 fp32（ARM 上 int8 不一定更快，必须实测）。
5. **记忆注入加「相关性门控 + MMR」**：当前这句话太短/与所有记忆都不相关时，只注入置顶与高重要性，
   不硬塞语义噪声；注入集合用 MMR（λ=0.7）去冗余，避免 5 条近义记忆占满预算。

## 1. 目标与非目标

**目标**
- 记忆：跨会话、可解释、可控制；同义/改口能召回；写入不重复、不矛盾、不静默。
- 菜品：几千到几万条菜品的口语检索与推荐短名单；离线可用；过敏安全。
- 性能：搜索 p95 < 50ms；每轮对话额外 < 30ms；首屏 0 阻塞。
- 隐私：嵌入在本机完成；不新增数据接收方。

**非目标**：跨设备同步、多用户/多角色空间、图谱数据库、文档 RAG、静默写入、云端 embeddings 作主路径。

## 3. 总体架构

```
写入侧（命令/页面/提炼/会话结束提议）
   └─ MemoryWriter ── 嵌入 ── 近重复(cosine) ── 合并/替换/新增 ── DB
菜品侧（目录/菜单/导入）
   └─ DishTagger（模型一次性打结构化标签）── 嵌入 ── DB

查询侧
  用户输入 ── 查询理解（别名/同义/槽位）── 嵌入
      │
      ├─ 硬过滤（过敏、营业、今日菜单、状态）
      ├─ 向量召回 topK ──┐
      ├─ 关键词（中文 bigram 倒排）──┤
      └─ 结构化标签匹配 ──────────────┤
                                      ▼
                              RRF 融合 + boost（置顶/重要性/口味/近期）
                                      ▼
                              MMR 去冗余 + 多样性约束
                                      ▼
                       搜索 UI（≤50） / AI 短名单（≤30） / 记忆注入（按预算）
```

四层可替换：`EmbeddingSource` / `VectorIndex` / `Ranker` / `MemoryWriter`；每层都有 fake 实现。

## 4. 嵌入层

### 4.1 模型

- 主选：**`bge-small-zh-v1.5` int8 ONNX，512 维，≈24MB，MIT**。
- P0 对照：`bge-base-zh-v1.5`（768 维，≈100MB）——若小模型在评测集上 recall@10 不达标再换；
  不预先背 100MB。
- 供应商 `nemotron`（2048 维，实测 2.0s/次）只作**质量上限基线**，不进运行时。

### 4.2 分词与输入

- Dart WordPiece（BasicTokenizer + WordpieceTokenizer，`[CLS]/[SEP]`，maxLen **64**）；
  **golden 分词测试**（中文、英文、数字、标点、emoji）。
- **maxLen 基准 32/64/128**：菜名/记忆都是短文本，64 通常足够；P0 实测决定。
- **前缀策略必须评测**：BGE v1.5 中文检索建议 query 侧加
  `为这个句子生成表示以用于检索相关文章：`；短菜名可能不加更好——P0 做 A/B，不凭感觉。
- 输出 L2 归一化；检索分数 = 点积。

### 4.3 运行时与并发

- `flutter_onnxruntime`（≥1.5.1，16 KB page 合规）。
- **长驻单 worker isolate + 命令队列**（不要每次调用新建 isolate）；intra-op threads=1（避免与 UI 抢核）。
- **已实现（2026-10-19）**：`embedding_worker.dart`——`embeddingWorkerMain`
  在 worker isolate 里加载模型并循环处理 embed 请求；主侧
  `EmbeddingWorkerConnection` 只 listen 一次（握手与后续消息共用同一条监听）、
  按 id 配对并发请求、worker 死亡 ⇒ 请求以 `EmbeddingUnavailable` 快速失败；
  `WorkerEmbeddingEngine` 惰性 spawn + `warmUp()`（首帧后预热，主线程零负担）。
  教训：主 isolate 上加载 24MB 权重会把低内存设备界面拖死（设备实测）。
- 批量：索引侧 ≤32 条/次；查询侧单条。
- **P0 必测 int8 vs fp32**：ARM 上动态量化有时因反量化更慢；以实测选型。
- 失败降级：模型加载/推理失败 → 关键词+标签检索，UI 如实显示「语义检索不可用」。

## 5. 索引层

### 5.1 表结构（schema 28）

```
embedding_index
  ownerType TEXT      -- 'dish' | 'memory' | 'food'
  ownerId   TEXT
  modelId   TEXT      -- 'bge-small-zh-v1.5-int8-v1'
  dim       INT
  encoding  TEXT      -- 'f32' | 'i8' | 'b1'
  textHash  TEXT      -- sha256(索引文本)
  vector    BLOB
  updatedAt DATETIME
  PRIMARY KEY (ownerType, ownerId)
  INDEX idx_embedding_model (modelId)
```

`ai_memories` 增列：`importance INT`（0–100，默认 50）、`lastUsedAt DATETIME`、`useCount INT`、
`supersededById TEXT NULL`、`expiresAt DATETIME NULL`（临时近况）。

`menu_items` 增列：`tagsJson TEXT`（结构化标签）、`ingredientsJson TEXT`（配料/过敏原标签，用户可改）。

### 5.2 一致性与生命周期

- **同一事务**：owner 增/改/删与索引行同事务（或先写 owner、索引异步补齐 + 启动 orphan sweep）。
- **textHash**：文本没变不重算；`modelId` 变全量重建。
- **批处理**：200ms 防抖、≤32 条/批、单事务写；可取消；进度「正在建立语义索引 120/800」。
- **重建触发**：模型变更、恢复备份后、首次启动、手动「重建索引」。
- **不入备份**：派生数据；恢复后后台重建，期间关键词可用。
- **规模三档**：≤5 万 int8 暴力；>5 万 1-bit（512 位=64B/条）Hamming 预筛 top 500 → int8 重排；
  >50 万纯 Dart HNSW。

### 5.3 文本组成

- 菜品：`名称｜地点·窗口｜档口｜标签（清淡/辣/汤/面/油炸…）｜营养摘要｜备注`，≤200 字。
- 记忆：`[kind/domain] 正文｜tags`。
- 食物（P4 可选）：`名称｜品牌｜分类｜营养摘要`。

## 6. 检索层

### 6.1 过滤：硬 vs 软

| 类型 | 规则 |
|---|---|
| **硬（安全/可用）** | 过敏与忌口（名称 + **配料标签**命中即排除）；饮食标签冲突；窗口当前/目标餐次营业；菜品属于今日 active 菜单（可选）；已删除/归档 |
| **软（偏好，扣分）** | 近 N 天吃过（默认 3 天，按天数衰减）；营养区间偏离；非偏好窗口；高油高盐（标签） |

> 只对**安全**做硬排除；偏好一律软惩罚，避免「过滤太狠导致没结果」。

### 6.2 候选与融合

1. 向量召回 topK=200；关键词 bigram 倒排 topK=200；结构化标签命中集合。
2. **RRF**：`rrf(x) = Σ_i 1/(60 + rank_i(x))`（三路）。
3. **Boost（乘法或加法，小权重）**：置顶 ×1.15；importance ×(0.9+0.2·norm)；个人口味相似 +0.05；
   近期已吃 ×0.85（软惩罚）；域匹配 ×1.05。
4. **MMR 去冗余**：`λ=0.7`，在 top 100 里选 N，避免近义重复（菜品同名多窗口、记忆近义）。
5. 截断：搜索 50；AI 短名单 30；记忆按预算档。

### 6.3 查询理解（低成本，高收益）

- **同义词/别名表**（可用户扩展）：清淡→清蒸/水煮/少油/少盐/汤；辣→麻辣/香辣/剁椒；面→面条/拉面/拌面；
  土豆↔洋芋、西红柿↔番茄。
- **槽位**：餐次（早/午/晚）、地点、窗口、忌口词、营养意图（高蛋白/低卡）。
- 槽位转成硬/软过滤与关键词扩展；**不额外调用 LLM**（延迟优先）。

### 6.4 记忆注入（query-aware + 门控 + MMR）

- `ChatEditContextBuilder.build({String? userMessage})`；对当前消息嵌入（**过短/纯表情则跳过**，
  只注入置顶 + 高重要性）。
- **相关性门控**：`max cosine < 0.35` ⇒ 语义路不参与，只保留置顶/重要性（避免噪声）。
- 排序：置顶 > RRF（语义+关键词+标签）> importance > 近期；域标签相近时 ×1.05。

> **2026-10-24 实测修正：门控的判据错了，已改。**
>
> 上面这条「只保留置顶/重要性」在**关键词路**上等于「字面没重叠就一条都不给」。
> 实测：用户存了「我喜欢清淡口味」「我不吃香菜」「我对花生过敏」，问
> 「今天吃什么 / 推荐个午饭 / 推荐个菜」——`bigram` 零交集 ⇒ `maxRelevance=0`
> ⇒ 门控 ⇒ 候选只剩「置顶 or `importance >= 80`」，而**默认 importance 是 50**
> ⇒ **六种说法全部注入 `[]`**。记忆系统实际不工作。
>
> **根因是判据而非参数**：记忆的价值恰恰在于「用户不会重复说」；要求这句话与
> 记忆**字面**相关才能想起来，等于要求用户每次复述一遍。
>
> **现行实现**（`memory_selector.dart`）：
> * 门控触发时，候选集 = **置顶 + 高重要性 + 「意图领域相符」**（`memoryDomainsInQuery`
>   用窄词表判饮食/训练/作息/食堂；**判不出就不兜底**，退回原行为）；
> * 领域兜底**上限 4 条**（`kMemoryGatedDomainFallback`）——存 20 条饮食记忆不会全塞；
> * 兜底排序 = **字面沾边 → 领域信号强度 → 重要性 → 近期**。只按重要性排会让
>   30 条同等 importance 的噪音把真正相关那条挤出去（实测踩过）；
> * 回归钉子：`test/features/ai_memory/memory_recall_effectiveness_test.dart`（17 条，
>   含「20 条饮食记忆最多带 4 条」「问饮食不夹带训练/作息」「打招呼≤2 条」等反向判据）。
>
> **仍未验证**：语义向量路（`kMemoryVectorGate = 0.35`）是否有同类问题——本次实测
> 环境里向量引擎未初始化，只修了关键词路。
- **MMR λ=0.7** 去冗余；预算三档 1.5k/3k/6k 字符（12/24/48 条），默认标准。
- 注入后 `lastUsedAt/useCount` **节流写**（≥10 分钟或会话结束批量），避免每轮写加密库。

## 7. 记忆治理

- **写入前**：嵌入 + 与 active 记忆比 cosine：
  - ≥0.96 判重 → 拒绝（快速路径：字符串相同也直接拒）；
  - 0.88–0.96 → **提议合并/更新**（返回候选 id + 建议动作）；
  - <0.88 → 新增。
- **改口/冲突**：旧条 `supersededById=新条`；检索只看 active；页面可看历史与恢复。
- **临时近况**：`kind=context` 可带 `expiresAt`（默认 30 天），到期提议归档（不自动删）。
- **时间语义（G23 / S14，schema 29，2026-10-19 用户授权）**：`ai_memories`
  +`validFrom`/`validTo`。新建即生效；改口把旧条 `validTo` 闭合（与
  `supersededById` 同时写，不删、可撤销）；`listAsOf(t)` 回答「t 时刻成立的
  是什么」，会返回已被改口但当时有效的旧条；记忆页有「按日期回看」
  （`ai-memory-asof`）。历史行迁移时回填 `validFrom = created_at`。
- **整理建议**：后台找 cosine≥0.9 的簇、长期未用（180 天且 importance 低）条目，进「整理建议」，
  用户确认才合并/归档。
- **自动提炼（默认开，进待确认队列）**：会话结束后台跑一次提炼，候选标注「新增/重复/相近/敏感」，
  下次打开记忆页可见；**永不静默写入**。
- **容量**：软顶 2000 / 硬顶 5000；UI 显示用量与「整理」入口。

## 8. 菜品与食堂

- **结构化标签（P1 重点）**：一次性用模型给每道菜打 `{spicy, oily, soup, staple, protein, veg, fried,
  steamed, sweet, cuisine}` + 配料/过敏原标签；用户可改。**这比向量更能解决「清淡/不辣/想吃面」**。
  标注任务离线批处理、可断点续跑、结果缓存；模型不可用时用规则词典兜底。
- **可用性**：硬过滤「今日 active 菜单 + 窗口营业 + 目标餐次」；目录里存在但今天没有的菜不参与推荐。
- **个人口味向量**：`taste = 近期吃过菜品向量（指数衰减）的质心`；`+0.05·cos(taste, dish)`；
  近期吃过 ×0.85 软惩罚。数据来自 meal → dish/food 的既有链路。
- **反馈（P4）**：推荐卡「换一个/不错」记录正负反馈，更新口味向量；不做静默学习。
- **AI 短名单**：top 30，按窗口分组，附标签与营养；保证多样性（至少各 1 个 veg/protein/staple）。
- **搜索 UI**：菜单 tab 搜索框（防抖 200ms），结果给「为什么推荐」（命中词/标签/营养/窗口）。
- **安全前提**：没有配料表时，过敏只能按菜名过滤——UI 必须如实标注「按菜名过滤，可能不完整」，
  并在 P1 补齐配料标签。

## 10. 评测（决定是否上线）

- **菜品集**：≥100 条中文口语查询（含方言/别名/多槽位）× 人工标注相关菜品；
  指标 **recall@10 / nDCG@10 / MRR**；**hard negatives**（关键词基线失败、语义应成功的样本）。
- **基线三档**：关键词+标签 → 向量 → RRF 混合；门槛：混合比「关键词+标签」**相对提升 ≥20%**，
  否则不上向量（说明标签已经够用）。
- **记忆集**：≥40 条同义/改口查询；top-5 命中 ≥90%；注入预算档位与 MMR 去冗余各一条判据。
- **模型健全性**：固定句对相似度断言——「番茄炒蛋 vs 西红柿炒鸡蛋」> 「番茄炒蛋 vs 红烧肉」；
  分词 golden；前缀策略 A/B；int8 vs fp32 延迟/质量。
- **回归**：现有 2521 条测试全绿；fake embedder 的确定性测试；真模型只在设备/基准跑。
- **设备**：模拟器 + 真机；飞行模式可用；低端机内存/耗时。

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0 尖刀** | ORT+分词；100 条查询评测；int8/fp32、maxLen、前缀 A/B；延迟 | 分词 golden；混合 vs 关键词+标签 ≥+20%；<15ms |
| **P1 结构化** | 菜品标签/配料标注（离线批处理）+ 索引底座 + 迁移 28 | 标签覆盖率；索引增量/重建/降级；安全过滤判据 |
| **P2 记忆** | query-aware、门控、MMR、三档预算、合并/替换、容量 2000/5000 | 记忆 top-5 ≥90%；冲突/合并/门控测试 |
| **P3 菜品** | 菜单搜索 UI、AI 短名单、口味向量、可用性过滤 | 设备帧+延迟；短名单多样性；过敏硬过滤 |
| **P4 规模化** | 二值预筛/HNSW、食物库语义搜索、反馈学习、会话结束提炼队列 | 压力测试；评测增益；反馈闭环 |

## 13. 风险与对策

| 风险 | 对策 |
|---|---|
| 分词/模型接错，向量全错但「看起来能跑」 | golden 分词 + 固定句对相似度 + 前缀 A/B |
| int8 在 ARM 反而更慢 | P0 实测 int8 vs fp32，按设备选型 |
| 过滤太狠导致无结果 | 硬/软分离；软惩罚 + 兜底「放宽条件」提示 |
| 过敏过滤不完整 | 配料标签 + UI 如实标注；没有标签时明确说「按菜名」 |
| 向量绕过硬约束 | 硬过滤先行 + 结果再过一遍约束断言（测试钉死） |
| 索引与 owner 不一致 | 同事务/异步补齐 + 启动 orphan sweep |
| 备份恢复后索引缺失 | 自动重建 + 进度提示 + 关键词兜底 |
| 低端机内存/发热 | worker isolate、分批、可暂停、语义检索可关 |
| 记忆变多注入变差 | 门控 + MMR + 预算档 + 评测回归 |

## 14. 明确不做

图谱数据库、文档 RAG、多记忆空间、跨设备同步、云端 embeddings 主路径、sqlite-vec/ObjectBox、
静默写入、自动删除记忆、用向量替代过敏等硬约束。

## 15. 与 v1 的差异（自审结论）

| 项 | v1 | v2 | 为什么 |
|---|---|---|---|
| 融合 | 手调加权和 | **RRF + 少量 boost** | 四种量纲不可比；RRF 免调参、抗单一信号支配 |
| 过滤 | 全硬过滤 | **硬/软分离** | 防止偏好过滤杀光结果 |
| 菜品质量 | 只靠向量 | **结构化标签+配料 + 向量** | 「清淡/不辣/面」是意图，标签比向量可靠 |
| 个性化 | 无 | **口味向量 + 近期惩罚 + 反馈** | 推荐质量的最大增量来自历史行为 |
| 性能 | int8 暴力 | **int8 → 1-bit 预筛 → HNSW 三档** | 不提前上重武器，也不在规模上来时无路可走 |
| 记忆注入 | 纯相关度 | **相关性门控 + MMR** | 短消息/无关消息不硬塞；去近义冗余 |
| 索引一致性 | 未写 | **同事务 + orphan sweep** | 派生索引最容易悄悄烂掉 |
| 使用度写入 | 每轮写 | **节流/批量** | 加密库写放大 |
| 评测 | 50 条 | **≥100 条 + hard negatives + nDCG** | 防止「看起来能用」 |

## 16. 模型选型与降级 FAQ

### 16.1 为什么不是 MiniLM

- `all-MiniLM-L6-v2`（384 维，int8 ≈23MB）是**英文通用**模型；中文菜名/记忆的检索质量明显弱于
  `bge-small-zh-v1.5`（512 维，≈24MB）。两者体积几乎一样，选中文专用。
- **离线要求没有变**：端上模型始终是主路径；变的只是模型。
- 需要多语言（英文菜名/留学生）时再评估 `multilingual-e5-small`（118MB）或 `bge-m3`（过大），v1 不做。

### 16.2 在线向量模型不可用了怎么办

- 运行时**不依赖**在线 embeddings：索引与查询都用端上模型；供应商 `nemotron` 只作评测基线。
  它下线/改名/限流都不影响用户。
- 若将来启用「云端高质量索引」模式，必须遵守：
  1. 同一时刻只有一个 active embedding profile（`modelId` 唯一）；**向量空间不可混用**。
  2. 供应商 404/400/超时 → 标记该 profile 不可用，**语义检索降级为关键词+标签**（不报错、不阻断）；
     已有本地索引保留但只读。
  3. 切换 profile = 全量重建；重建期关键词兜底；绝不静默混用两套向量。
  4. 任何 profile 都必须有端上兜底模型，否则不允许设为默认。
- 端上模型自身失败（资产损坏/CPU 不支持/内存不足）：同样降级 + 如实提示「语义检索不可用」+
  重试/重建入口；不阻断记餐、关键词搜索与记忆注入（置顶/重要性仍可用）。

### 16.3 模型更新

- `modelId` 带版本；更新 = 后台重建，完成后原子切换；旧索引保留到新索引可用（可回滚）。
