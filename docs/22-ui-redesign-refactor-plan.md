## §2 改造策略

### 2.1 为什么不做"就地修改"

考虑过三种策略：

| 策略 | 评估 |
|---|---|
| A. 就地逐处修改现有 widget | **否决**。差异是结构级的（半圆环→全圆环、Bento→白卡、悬浮胶囊→贴底栏），就地改等于把每个 widget 重写两遍，且中间态难以测试 |
| B. 新建平行目录，完成后切换 | **否决**。会产生两套设计系统共存期，旧的新引用不断产生，切换时仍有大量测试需要一次改写 |
| **C. 分层推进：底座先换，再逐页重建** | **采用**。底座（token + 组件 + 底栏 + 路由 + schema）一次性换到底，之后每页可独立完成、独立验证。中间态是"底座新、部分页面旧"，但**始终可编译、可测试、门禁可绿** |

### 2.2 硬边界（Whole-Change不变量）

| 边界 | 内容 |
|---|---|
| **数据不丢** | 37 张逻辑表及其数据在改造全程不得丢失或变形。迁移只增不改不删 |
| **行为不丢** | 114 个纯行为测试文件的行为断言逐条保留 |
| **门禁不红** | 每个阶段结束时 `tool/verify.bat` 必须 EXIT=0。不接受"暂时红着后面修" |
| **依赖不变** | 除录音插件外不新增运行时依赖。图表改手绘 `CustomPainter`（`fl_chart` 保留但新页面不用） |
| **隐私不变** | 全数据本地 + BYOK + SQLCipher fail-closed。除录音权限外不加权限 |
| **诚实不变** | 无数据一律空态，绝不用设计稿示例值（`docs/21` §6.1） |

### 2.3 token 迁移的关键决策：新增具名 token，不改现有值

现有 `AppDimens.spaceSmall = 12`、`pagePadding = 20`，被大量页面引用。新设计是 `spaceSmall = 8`、`pagePadding = 16`。

**若直接改值，会在无人察觉的情况下静默改变所有未迁移页面的间距**——这与"逐页重建、逐页验证"的策略冲突。

**决策**：

1. `AppDimens` **新增**具名 token：`spaceMicro 2`、`spaceTiny 6`、`spaceSmall 8`（新名 `spaceSmallNew` 太丑 —— 实际做法见下）、`spaceMediumPlus 14`、`spaceLargePlus 20`、`cardGap 16`
2. 具体做法：**新建设计 token 文件按新规范定义一套具名常量**（如 `NewDimens.pagePadding = 16`），旧常量标注 `@Deprecated` 并附"新页面请用 X"，**阶段 I 收口时统一删除旧常量并全局迁移剩余引用**

> 实施细节在阶段 A 定稿时确认；原则是"新页面绝不读到旧值，旧页面绝不因改造而变样"。

同理适用于颜色：新设计的中性色与 ramp 值在**新的 token 组**里定义，旧常量保留至阶段 I 删除。

### 2.4 逐页完成的定义

一页算"完成"必须同时满足：

1. 结构与设计稿 DOM 逐节点对应（差异需在证据文档里说明理由）
2. 数据来自真实仓储，无硬编码示例值
3. 空态按 `docs/21` §6.1 处理
4. 该页的视觉测试按新 Key 改写，且**每个新测试都做过隔离变异红证**
5. 模拟器截图与 `ui设计/pages/*.html` 并排比对，差异列入证据文档
6. `tool/verify.bat` EXIT=0
