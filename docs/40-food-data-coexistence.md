# 食物数据共存模型：食物库 / 食堂菜品 / 菜品库 / 餐记录（`docs/40`）

日期：2026-10-18
状态：**方案稿（未实施）**。数据模型变更（新列 + 链接），范围变更 **S13**；
与 `docs/39` 的 S12（向量检索）统一排期：同批落地则合并为一次迁移，否则 S13 先（schema 28）、S12 后（29）。
前置：`docs/03` §12、`docs/21` §5.3、`docs/38`。

## 0. 结论：三层数据 + 一层快照，四条铁律

```
食物库 foods            = 营养事实库（每 100g；导入目录 + 自建）——「算账用」
食堂菜品 menu_items     = 供应事实（某地点/窗口今天卖什么；图片/证据/可用性）——「有什么」
菜品库 dish_library     = 你的份量模板（一份多少克、哪一餐、来源）——「怎么记」
餐记录 meal_items       = 不可变快照（这次吃了多少、当时营养值）——「吃过了」
```

四条铁律：

1. **营养只有一个口径：每 100g。** 「一份」是份量（`servingGrams`），不是营养口径；
   任何「每份 kcal」都必须能还原成 `per100g × servingGrams / 100`。
2. **身份只认显式链接，不靠猜。** 名称归一化 + 别名只能产生「建议关联」；
   确认后的链接存表（`menu_item_food_matches` 复用 + `dish_library.source*`）。
3. **餐记录只存快照。** 来源（食物/菜品/食堂菜）之后怎么改，都不回写历史记录。
4. **来源与证据永远可见。** 每条数据都标「导入库/自建/食堂分析/AI 估算/用户确认」，
   并允许「有更新」提示；同步必须用户确认，不静默覆盖。

## 1. 现状与问题（已核对代码）

| 表 | 现状 | 问题 |
|---|---|---|
| `foods` | 每 100g；导入 2 万行 + 自建；有别名/份量/证据/分类 | 好，保持 |
| `menu_items` | 名称/档口/图片/状态；营养在 `menu_item_nutrition_evidence`（**每 100g**，带区间/等级/来源） | 没有「一份多少克」；与食物库只有导入期的匹配表 |
| `dish_library` | 名称/餐次/**每份** kcal 与三宏量/供应时段/来源/点评/图片 | **没有 servingGrams**；食堂复制进来时把 per100g 当 perServing；没有来源 id |
| `meal_items` | 名称快照 + 克数 + 四营养快照；`foodId` 可空 | 没有来源类型/id；菜品与食堂菜只能靠备注辨认 |
| `menu_item_food_matches` | menuItem ↔ food，`suggested/confirmed/rejected` + confidence | 只用于导入匹配，未被「菜品库/餐记录」复用 |

两个已写进代码的「100g 假设」：
- `AddCanteenDishesToLibrary`：把食堂 per100g 直接写进菜品库的「每份」列；
- `AddDishToMeal`：记一笔 `grams=100`、营养按整份填。
两处注释都承认这是假设。**有了 `servingGrams` 就能把这个债还掉。**

## 2. 目标模型

### 2.1 字段增量（纯加法）

`dish_library`：
- `nutritionBasis TEXT`：`perServing` | `per100g`（历史行回填 `perServing`）
- `servingGrams REAL NULL`：一份多少克（历史行回填 `100`，并标 `basisAssumed=1`）
- `basisAssumed BOOL`：份量是否是假设值（UI 显示「按 100g 估算」）
- `sourceType TEXT NULL`：`canteen` | `food` | `manual` | `imported`
- `sourceId TEXT NULL`：menuItemId / foodId（**不加外键**，允许来源删除后悬空）
- `sourceUpdatedAt DATETIME NULL`：来源最后一次营养变更时间（用于「有更新」）
- `userEdited BOOL`：用户改过营养/份量（同步时不覆盖）

`menu_items`：
- `servingGrams REAL NULL`：这个窗口一份大概多少克（可空；分析时估或用户填）
- `tagsJson TEXT`：结构化标签（清淡/辣/汤/面/油炸…，见 docs/39 §8）
- `ingredientsJson TEXT`：配料/过敏原标签（过敏硬过滤的前提）

`meal_items`：
- `sourceType TEXT`：`food` | `dish` | `menu_item` | `scan` | `manual`（历史回填：foodId 非空→food，否则 manual）
- `sourceId TEXT NULL`

链接：**复用 `menu_item_food_matches`**（menuItem ↔ food），补一条查询索引即可；
不新建「万能链接表」——两两关系只有这一种，复用现成的更稳。

### 2.2 不变量（测试钉住）

```
dish.kcalPerServing = round(dish.per100gKcal * dish.servingGrams / 100)   // 单一事实源
meal_item.kcal      = 记录时快照（不随来源变化）
menu_item 营养      = per100g 代表值（区间另存，不用中点冒充）
```

- `dish_library` 的四个展示列（kcal/蛋白/碳水/脂肪）保持「每份」语义（兼容现有 UI），
  但**写入时必须由 per100g × servingGrams 计算**，并记录 basis。
- 若 `servingGrams` 为空/假设：UI 明确显示「按 100g 估算」，不假装知道份量。

### 2.3 食物库到底用在哪（价值清单）

| 场景 | 为什么必须是食物库 |
|---|---|
| **自己做饭 / 按食材记录** | 食堂菜和菜品库都是「整份」；只有食物库有 per100g 的食材值（200g 米饭 + 150g 鸡胸肉 + 10g 油） |
| **包装食品** | 品牌/规格级条目（一瓶牛奶、一包饼干），食堂菜和菜品库都没有 |
| **拍照识别** | 识别出「米饭/鸡蛋」后必须匹配到食物才能算营养 |
| **离线查询** | 不联网、不调 AI 也能回答「100g 豆腐多少蛋白」 |
| **AI 估算的对照** | 同名食物（120 kcal/100g，verified）vs AI 估算（150，C 级）并排显示，差异大时提示你判断 |
| **营养目标 / 计划** | 每日缺口、宏量比例、计划求解都依赖可计算的 per100g 数据；自做饭没有替代 |
| **数据可审计** | 来源/许可证/版本/证据等级都在；AI 估算是不可审计的猜测 |
| **CSV 契约** | 21 列导入导出，数据可迁移、可备份 |

**结论**：食物库不是「食堂菜的数据库」，是**营养计算器与事实底座**；食堂菜是「供应事实」，
菜品库是「份量模板」。如果你只吃食堂，它在日常路径里只当参考——但在自做饭、包装食品、拍照、
离线、对照这五个场景里，没有替代品。

### 2.4 让食物库在 UI 上「看得见」（建议）

- **记录餐两个入口**：「按食材记录」（食物库，per100g × 克数）/「按菜品记录」（菜品库/食堂，每份）。
  现在两个入口混在一起，用户自然觉得食物库没用。
- **建食堂菜**：命中时给「参考食物库」chip（不默认填），并排显示两者营养。
- **AI 对话**：发送前由 App 做一次**本地食物名预检索**，把 top 3 命中（名称/per100g/来源）
  作为「食物库参考」段注入 systemContext——模型看不到 2 万行，但能看到本次相关的 3 条。
- **菜品库**：新建时支持「从食物库组合」（配料），这是自做饭的主入口。
- **拍照识别**：结果页显示「匹配到食物库：米饭（116 kcal/100g，来源 xx）」，匹配不到才标估算。

### 2.5 配料与过敏原：来源、权威与存储（2026-10-18 补）

**先纠正一个事实**：`foods` **没有**配料/过敏原字段——`dietaryLabelsJson / allergensJson` 已随
schema 22 删除（`docs/31` §2 D5），21 列 CSV 也没有；每日计划 solver 的 `allergen_conflict`
因此**失去了唯一输入源**，代码里如实记着这条代价。所以「引用食物库的配料」这条路**目前不存在**，
配料必须另有来源；顺带说明：本方案落成后，solver 也能第一次拿回食物侧输入。

**三个来源，一条优先级**（用户 > AI > 词典）：

| 来源 | 何时用 | 说明 |
|---|---|---|
| **用户输入/确认**（权威） | 任何时候都能改；改过就 `userEdited=true` | chip 形式增删；给常用词表 + 本地过敏原词库（离线可用）；**AI 之后不再覆盖** |
| **AI 打标**（默认起草） | 配了 AI 时，**与营养分析合并成一次「菜品分析」调用** | 输出限定词表：主要食材 / 烹饪方式 / 口味；每项带置信度；不确定就标「不确定」，不硬猜 |
| **本地词典/规则**（离线兜底） | 没 AI 或 AI 失败时 | 按菜名关键词推测（蛋/奶/虾/蟹/花生/坚果/鱼/面/米/鸡/牛/猪/豆腐/芝麻…）+ 分类弱提示（如食物库二级分类=豆制品 → 大豆） |

**存储与推导**（单一事实源）：

- `menu_items.ingredientsJson`：食材 key 列表（每项 `{name, source, confidence}`）；
  `menu_items.tagsJson`：烹饪/口味/餐次标签。
- **过敏原不单独存，由食材推导**：`蛋→蛋类`、`牛奶/奶油/奶酪→乳制品`、`面粉/面条→麸质`、
  `虾/蟹→甲壳类`、`黄豆/豆腐/豆浆→大豆`、`花生→花生`、`核桃/腰果→树坚果`、`鱼→鱼类`、`芝麻→芝麻`。
  避免「改了食材忘了改过敏原」。
- **过滤规则**：用户忌口是自由字符串（含「芒果」这类具体食材）⇒
  `忌口词 ∩（食材名 ∪ 食材别名 ∪ 过敏原组名）`，归一化后匹配。
- **状态徽标**：`配料：已确认 / AI 推断 / 关键词推测`；未确认的菜在推荐卡上标注（策略见 `docs/41` D9）。
- **诚实边界**：没有配料数据的菜**不假装安全**——宁可标「未确认」，也不写「不含 X」。

**批量与成本**：打标与营养分析同一个队列（并发限流、断点续跑、跳过已完成、可暂停）；
优先处理「已被记过餐 / 出现在推荐里 / 用户打开过」的菜，剩下的按需。

**导入食物库怎么办**：2 万行不可能逐个 AI 打标 ⇒ 只对**用户自建食物**与**食堂菜品**打标，
导入行用分类启发式（二级分类/菜系 → 食材组）并标「推测」，用户用到时可一键补标签。

## 3. 写入路径矩阵（谁写谁、默认值是什么）

| 用户动作 | 写入 | 默认份量 | 营养来源 | 备注 |
|---|---|---|---|---|
| 食堂菜品「加入午餐」 | `meal_items`（快照） | `menu_items.servingGrams ?? 100` | 食堂证据 per100g × 克数 | 来源 `menu_item`；无份量时提示「按 100g 估算」 |
| 食堂菜品「存为菜品」 | `dish_library` | `servingGrams ?? 100`，`basisAssumed=!hasServing` | 食堂证据 per100g | `sourceType=canteen`、`sourceId=menuItemId`；同名已有则提议关联/更新，不盲目新增 |
| 食物库「记录食用」 | `meal_items` | `foods.defaultServingGrams ?? 100` | 食物 per100g × 克数 | 来源 `food` |
| 菜品库「加入餐」 | `meal_items` | `dish.servingGrams ?? 100` | 菜品每份值（按克数缩放） | 来源 `dish`；缩放用 `grams/servingGrams`，不是再乘 100g |
| 拍照识别 | `meal_items` | 识别给的克数 | 匹配到的 food 或估算 | 来源 `scan`；匹配不到时 `sourceId=null` 并标估算 |
| AI 对话「我吃了…」 | `meal_items` | 按命中的来源 | 按命中的来源 | 见 §5 路由 |

**所有路径最终都落到同一个 `MealRepository.create`**：来源只影响默认值与备注，不产生第二套记账逻辑。

### 3.1 新增食堂菜品时，食物库已有同名条目怎么办

**现状（已核对代码）**：`canteen.dish.create` 只收 `window` + `name`；建完不会查食物库，也不会自动填营养。
营养只在你点「AI 分析」后由 `canteen.dish.nutrition` 写入，且 `recordNutrition` 一律
`origin='ai_estimate'`。仓库里已有 `MenuItemMatcher.suggestMatches()` 与 `menu_item_food_matches`
链接表，但只在菜单 tab 的匹配 UI 里调用，**建菜时不会自动跑**。

**目标行为：给建议，不静默填。** 建菜/改名成功后，App 本地跑一次匹配
（精确名 → 别名 → 归一化 → 可选向量），命中就弹出三选一：

| 情况 | 默认建议 |
|---|---|
| 食物库**精确同名**且来源可靠（`verified`/导入库） | **引用食物库营养**（默认）；「AI 重新分析」为次选 |
| 只有别名/模糊匹配，或食物是自建低置信 | 不预选；两个选项都给 |
| 食物库没有 | 直接走 AI 分析（现状） |
| 用户明确说「用食物库的」 | 引用；不调 AI |
| 用户明确说「按食堂做法重新分析」 | AI 分析；链接保留为 `suggested` |

引用时：把食物库的 **per100g** 值复制进 `menu_item_nutrition_evidence`，
`origin='food_library'`、`grade` 沿用食物的证据等级、`confidence` 取匹配分，
并把 `menu_item_food_matches` 置 `confirmed`。

**为什么不自动填**：食堂做法（油/盐/份量）与通用食物条目可能不同；自动填会把「引用」伪装成
「实测」。所以默认是「建议 + 你点一下」，且界面上永远标来源（食物库 / AI 估算 / 用户输入）。

**AI 对话里怎么走**：模型看不到 2 万行食物库（快照只带自建食物），所以由 **App 侧执行器**
在 `canteen.dish.create` 成功后跑匹配，并把两个动作作为结果里的可点按钮返回
（复用现有「缺实体 → 修复按钮」的形态）；同时给 `canteen.dish.create` / `canteen.dish.nutrition`
增加可选参数 `nutritionFrom: 'food' | 'ai' | 'none'`（缺省 `none`/`ai`，旧行为不变），
让用户明确说「用食物库的」时能直接落库。

## 4. 去重与关联

> **as-built（2026-10-24 用户裁决）**：「加入菜品目录里不能自动加入菜品库吗…
> 我希望他们就是一个库，不要分开，不要自己加入。这样就不需要整理重复菜品和
> 关联到食堂菜品」。据此：
> * **食堂目录 ↔ 菜品库不再是两个库**：食堂菜写出营养即**自动**进菜品库
>   （`(sourceType='canteen', sourceId=menuItemId)` 是身份键），改名/改份量
>   更新同一行，删菜/删窗口/删地点跟随删除。手动入口（`canteen-add-to-library-<id>`）
>   与「整理重复菜品 / 关联到食堂菜品」整族（页面 `/food-cleanup`、设置行
>   `settings-food-cleanup-row`、`loadDuplicateSuggestions`）**全部退役**。
> * 下面第 2 条第 3 项（「手动建的同名菜 → 提示已存在，关联还是新建副本？」）
>   与 §9 的 P4「重复菜合并建议」随之作废；`sourceId` 唯一 + 自动同步就是
>   这一层的全部机制。
> * **仍然成立**：菜品库 ↔ **食物库**是两个东西（每 100g 事实 vs 我的份量
>   模板），同名同物的「建议关联」、配料链接、营养冲突并排显示都不变。

1. **归一化**：全半角、大小写、空白、常见标点；中文别名表（土豆↔洋芋、西红柿↔番茄、面↔面条）。
2. **候选关联**（只产生建议，不自动合并）：
   - 食堂菜 ↔ 食物库：名称精确/别名/包含 → `menu_item_food_matches(status=suggested, confidence)`；
   - 菜品库 ↔ 食堂菜：`sourceType=canteen` 时按 `sourceId` 唯一；手动建的同名菜 → 提示「已存在，关联还是新建副本？」；
   - 菜品库 ↔ 食物库：一道菜可以关联多个食物（配料），但**菜品本身不是食物**，不做一对一同义。
3. **确认后才生效**：`confirmed` 的链接用于展示「已关联」与营养对照；`rejected` 不再提示。
4. **禁止**：按名字自动合并、自动覆盖营养、把食堂菜直接写进 `foods`（生命周期不同）。

### 4.5 食物库与菜品库重叠时到底怎么处理

重叠是**正常且允许**的（食物=每 100g 事实，菜品=我的份量模板），关键是「不重复计数、不互相覆盖」：

| 场景 | 处理 |
|---|---|
| 同名同物（导入库的「番茄炒蛋」vs 食堂的「番茄炒蛋」） | 生成「建议关联」；确认后搜索合并为一条主结果（类型徽标 +「食物库也有」），记餐只选一个来源 |
| 同名不同物（两个窗口份量不同） | 不合并；`sourceId` 区分；菜品库允许同名多行，UI 标来源窗口 |
| 菜品是多个食物的组合（配料） | 用配料链接/`ingredientsJson`，**不是**身份链接；一道菜可关联多个食物 |
| 营养值冲突 | 并排显示两者与证据等级，默认高置信度；用户可改；**绝不静默覆盖** |
| 记餐 | 一次只产生一条 `meal_item`，`sourceType` 记录来源；不会两边各算一次 |
| 清空内置食物/删地点 | 链接悬空 → 显示「来源已删除」，菜品自身营养保留；不级联删菜品 |
| 统计口径 | 「食物库 N 条」「菜品库 N 道」分开计数；关联对显示「1 道菜（关联 1 条食物）」，不合并计数 |

## 5. AI 路由（对话里怎么选对系统）

协议补一条「食物来源优先级」（只改提示词，不改 wire 形状）：

```
用户说「我吃了/在食堂吃了 X」：
1) 今天/目标日期在该地点窗口有同名菜品（menu_items + 今日 active 菜单）→ 用食堂菜（带份量/窗口）；
2) 菜品库有同名菜（dish_library）→ 用菜品库（每份口径）；
3) 食物库有同名食物（foods，精确/别名）→ 用食物库（每 100g × 克数）；
4) 都没有 → 按现有规则提议 food.create（自建食物），并说明「已建成食材，下次可直接记」。
用户说「食堂今天有什么」→ 只查菜单，不查食物库。
用户说「这个菜多少卡」且指食堂菜 → 用食堂证据并标「AI 估算/证据等级」。
```

配套命令（加法）：
- `meal.create` 的 items 增加可选 `kind`（`food|dish|menuItem`）与 `ref`（id 或名称）；
  缺省仍按 `food` 解析，**旧行为不变**。
- 新增 `dish.link`（把菜品关联到食堂菜/食物）——可选，先由 UI 做，命令后置。

## 6. 同步语义（2026-10-24 改写，`RV4-P2-09` / `docs/56` R10-c / 裁决 D2）

**结论一句话**：**自动同步是唯一路径；用户手改即冻结。**

- 食堂菜重新分析营养 → 更新证据 + `menu_items.updatedAt` → **自动**同步到菜品库
  的同一行（身份键 `(sourceType='canteen', sourceId=menuItemId)`）。
  覆盖七条写路径：建菜 / 改名 / 换照片 / 写营养 / 删菜 / 删窗口 / 删地点。
- **`userEdited` 行冻结**：`DishLibraryRepository.upsertBySource` 检测到
  `existing.userEdited == true` 时，**营养四值与来源证据保留用户的值**
  （`_updatedPreservingUserNutrition`）；菜名/餐次/照片/窗口/份量这些「来源侧的
  排布事实」仍跟随来源。用户想解除冻结：在菜品库编辑那一行（会重新置位
  `userEdited`）或删除重建。
- **「陈旧提示 + 手动同步」整族退役**（裁决 D2）：既然自动同步覆盖全部写路径、
  手改行又被冻结，「食堂营养有更新 + 点同步」这套交互已无对象。相关 Key
  （`nutrition-menu-dish-stale-*` / `nutrition-menu-dish-sync-*`）与组件一并删除，
  `dish_staleness.dart` / `dish_source_sync.dart` 不再有 UI 使用者。
- 餐记录**永不同步**（快照是历史事实）。
- 来源被删除（地点/窗口/食物清空）：链接行跟随删除（`deleteBySource`），不留幽灵。
- **旧行为对照（如实留档）**：改前是「UI 提示陈旧 + 用户点同步」，且自动同步会
  **覆盖**用户手改的营养值——那是本批修掉的数据语义缺陷（用户改的数被悄悄改回去
  比不更新更糟）。

## 7. 统一检索与展示

- 一个 `FoodSearchService` 同时查 `foods` / `menu_items` / `dish_library`，返回
  `FoodHit {type, id, name, nutritionBasis, kcal, sourceBadge, availability}`；
  排序：精确名 > 别名 > 关键词 > 语义（S12 落地后）。
- 搜索/记录 UI 用类型徽标区分：`食物` / `食堂菜` / `我的菜`；食堂菜显示窗口与「今日有」。
- 餐记录卡片显示来源徽标（食物/菜品/食堂/扫描/手动），长按可看「来源与证据」。
- AI 短名单同时可含三类，但**同一道菜只出现一次**（按链接去重，优先今日食堂菜）。

## 8. 迁移与兼容

- schema 28（**与 S12 合并为一次迁移**，总表见 `docs/41` §11）：`dish_library` 7 列、`menu_items` 3 列、`meal_items` 2 列，
  全部存在性守卫、纯加法。
- 回填：
  - `dish_library`：`nutritionBasis='perServing'`、`servingGrams=100`、`basisAssumed=1`；
    `sourceType` 由现有 `source` 推断（`ai_estimate`+有供应时段 → `canteen`，否则 `manual`）。
  - `meal_items`：`foodId` 非空 → `sourceType='food'`，否则 `manual`。
- 备份：新列随表；**CSV 21 列契约不动**。
- 清除：`allTables` 自动覆盖。
- 回滚：新列可空，旧代码忽略即可；不做破坏性迁移。

## 9. 分阶段

| 阶段 | 内容 | 价值 |
|---|---|---|
| **P1 统一体验（不动 schema）** | 统一搜索（三类结果 + 徽标）；AI 路由提示词；餐记录来源备注；食堂菜「加入午餐」提示「按 100g 估算」 | 立刻不再「两套系统各找各的」 |

| **P4 整理** | 关联建议批量确认、陈旧同步批量处理、重复菜合并建议 | 数据长期不烂 |

## 10. 验收判据

- 同一道「番茄炒蛋」在食堂/菜品库/食物库同时存在时：搜索只出现一条主结果 + 关联说明；
  记一餐只产生一笔，不重复计数。
- 食堂菜 per100g=150、servingGrams=250 ⇒ 菜品库显示 375 kcal/份；改 servingGrams=200 ⇒ 300 kcal/份；
  餐记录写 250g ⇒ 375 kcal 快照，之后来源改营养不影响这条历史。
- 没有 servingGrams 的菜：UI 显示「按 100g 估算」，不显示成确定份量。
- 食堂重新分析 → 菜品库出现「有更新」；用户点同步才变；`userEdited` 只提示。
- 过敏：菜品有配料标签时按配料硬过滤；没有标签时 UI 明确「按菜名过滤，可能不完整」。
- 备份往返：新列保留；CSV 表头仍是 21 列；全清覆盖。
- 门禁：format / analyze / 全量测试 + 上述新判据。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 同名不同物（两个窗口的「番茄炒蛋」份量不同） | 身份键含来源（menuItemId），名称只用于建议；菜品库允许同名多行但提示 |
| 导入库里的「菜」与食堂菜重复 | 只做建议关联，不自动合并；餐记录按用户选择的一种来源记 |
| 回填把历史份量当成 100g | `basisAssumed=1` 明示；不改历史餐记录 |
| 同步覆盖用户手改 | `userEdited` 守卫 + 只提示 |
| 过敏过滤仍不完整 | 配料标签 + UI 如实说明（S12 §8 同款） |

## 12. 明确不做

- 不把 `foods` 与 `menu_items` 合成一张表（生命周期、来源、证据都不同）。
- 不按名称自动合并/自动改营养。
- 不改 21 列食物 CSV 契约。
- 不让菜品库承担「营养事实源」角色——它只是份量模板。
