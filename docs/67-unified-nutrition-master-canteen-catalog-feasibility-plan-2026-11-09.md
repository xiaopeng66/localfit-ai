## 0. 一页结论

### 0.1 唯一推荐路线

**采用用户提出的“大库＋食堂引用”方案，并进一步约束为：一个营养事实源、独立的供应关系、不可追溯改写的记餐快照。**

- **统一食物库**：食材、包装食品、成品菜都放进来，营养统一按每 100g 保存。物理上优先复用和扩展 `foods`，不另造第四个营养库。
- **香园／食堂目录**：一条供应记录表示“某窗口供应这道菜”。通过稳定 ID 引用主库，自己维护每份克数、实际图片、展示名和供应时间等信息。
- **饮食记录**：保存“这次吃了多少克、当时按什么营养算、最后计入多少”的快照。以后修改主库或份量，不重算已经记下的餐。
- **旧独立菜品库**：逐步停止每份营养的独立写入，保留必要的旧 ID、原始资料和待补全兼容能力；不长期维持两套可编辑营养。

```text
统一食物库 foods                         食堂供应 menu_items
宫保鸡丁·常规做法（foodId=A） ──────────→ 一窗口（menuItemId=M1，每份200g、实拍图）
  每100g营养、来源、修订        └────────→ 二窗口（menuItemId=M2，每份250g、实拍图）

宫保鸡丁·二窗口偏油（foodId=B） ────────→ 若做法确实不同，二窗口改引用B
  独立每100g营养，保留变体关系

选食物＋克数 / 选供应＋份数 → 统一换算成克数 → 保存本次记餐快照
```

**“一库”指唯一的当前营养事实，不是把营养、窗口、照片、历史餐全部塞进一张表。** 多张关联表、营养修订和来源证据不等于多套互不相通的营养库。

### 0.2 对用户问题的直接结果

用户让 AI“把宫保鸡丁存到库里”后：

1. 它进入统一食物库；食物库、记餐选食物、食堂新建供应时的选食物，三个入口都能找到同一 ID。
2. 没有指定窗口，不会凭空出现在某个窗口的供应列表，也不会被记成吃过。
3. 用户随后在一窗口选择它，填写“一份 200g”和图片，即完成上架，不需要再录一遍营养。
4. 若用户一次说“新建宫保鸡丁，放到一窗口，一份 200g”，可以在一个操作流程中完成建库和挂窗，并分别回执。

### 0.3 本方案的核心优化

| 容易失败的做法 | 本方案的固定决策 |
|---|---|
| 只把三个搜索列表拼在一起 | 统一实体 ID、写入服务和营养计算；搜索只是同一主库的不同投影 |
| 食堂选择食物后复制一份营养 | 供应保存主库引用；当前营养从主库修订读取，按份值派生 |
| 所有同名菜自动合并 | 名字只检索；同名不同做法、品牌或营养允许并存 |
| 每份重量缺失就补 100g | 明确未知；可先建供应，按份记餐前必须补重量或改填实际克数 |
| 共享营养一改，所有窗口被暗中改掉 | 展示影响范围；窗口局部重估默认建立变体，共享修订须明确选择 |
| 把旧“每份”字段改名为“每100g” | 只有可信重量才换算；无法判断的原样保留并标待补全 |
| 先做新页面，最后才管旧备份和旧卡片 | 兼容转换、旧 ID 和恢复规则在 P0/P1 前置设计 |

## 2. 目标、非目标与默认决策

### 2.1 必须达到的目标

- G1：所有新建、导入和 AI 创建的可计算食物，都以每 100g 营养进入同一主库。
- G2：食堂可从主库选取，也可在同一流程中新建；不要求用户重复维护营养。
- G3：三个选食物入口可发现同一实体；食堂供应列表只显示实际挂窗的供应。
- G4：份数只是一种输入方式，最终以实际克数和当时主修订生成记餐快照。
- G5：旧数据、旧 `.lfb`、旧引用和持久化 AI 卡片有明确兼容结果，不静默改变单位。
- G6：做法差异、来源不确定、份量未知、缺营养和冲突都可解释，不用假数掩盖。

### 2.2 本轮未来开发也不顺带做的事情

不重做现有十类食物分类；不复活价格、已退役的食物侧过敏原列、食谱或手动同步流程；不重构记忆系统、嵌入模型或整个导航；不要求内置库重新随安装包灌入；不引入云端营养主库；不把 CSV 升格为完整备份；不承诺从照片精确测得重量。

用户已有的内置／导入食物与自建条目共用主库，不因来源不同再分成互斥数据库。是否随包提供内置数据保持现有发布策略。

### 2.3 实施中不再临时摇摆的决策

| ID | 固定默认决策 |
|---|---|
| D01 | 主库复用 `foods`；供应复用 `menu_items`；不新增平行可写菜品营养库 |
| D02 | 主食物 ID 与供应 ID 独立，改名不换 ID；名称不构成唯一键 |
| D03 | 同做法不同份量共享主食物；不同配方／品牌／生熟口径建立不同条目，可记录变体关系 |

## 3. 目标数据契约

本节是待实施的逻辑契约，不是现有字段清单。新增列名、DTO 和索引在 P0 钉测试、P1 落 schema；主从边界和单位不能在施工中改变。

### 3.1 统一主条目：是什么、每 100g 多少

复用 `foods`，保留现有 ID、名称、品牌、来源、分类、许可与用户创建属性；按需要增量增加以下语义：

| 数据 | 建议归属与规则 |
|---|---|
| 当前营养 | 四项完整的每 100g 值＋当前生效修订 ID。主表四项是该修订的查询投影，不能独立于修订被另一条链路修改 |
| 身份差异 | 名称、品牌、做法／生熟说明；可空的变体父 ID 或关系。不能仅凭“成品菜”字样建立新分类体系 |
| 别名 | 复用既有别名能力，供搜索，不作为自动合并证明 |
| 通用份量 | 复用 `FoodPortions`；例如“一碗 150g”供主动选择，与窗口份量分开 |
| 来源与状态 | 关联证据／修订；区分人工输入、标签、引用数据、AI 估算、历史转换。来源不是准确性的保证 |
| 生命周期 | 可用／归档；归档不破坏历史与既有供应详情，可阻止新的挂窗或推荐 |

**当前 `foods` 四项非空，不在第一版把它放宽成一批空壳食物。** 创建可计算主条目须四项齐全且合法；缺项可保存为分析草稿或未分析供应，不插入一行假零食物。已有不完整营养修订保留为未生效资料，不能顶替完整生效修订。

### 3.2 营养修订与证据：可以保留历史，不能各自成为当前事实

复用 `FoodNutritionRevisions` 及既有证据能力：

1. 给既有完整主食物建立基线修订；以后一次营养修改在同事务内追加修订、切换生效指针并更新主表投影。
2. 当前消费者统一读取“主食物＋生效完整修订”；不能有页面取主表旧值、另一个取食堂证据最新值。
3. 修订保存来源、质量／估算标志、原始口径、原始数值、转换重量及其来源。旧每份值不能只留下换算后的结果。
4. 现有热量区间与代表值分开保留；只有区间没有代表值时，不自动取中点伪装完整营养。
5. 旧菜品已有的纤维、钠、维生素 D，按已知单位增加可空的每 100g 修订字段；仅在口径与换算依据明确时转换。未知仍为空，不填零。
6. 图片、点评、来源文本和不能确定单位的旧扩展值，保留原始资料及可查看入口；不能为了四项统一丢掉，也不能把“mg”当“g”缩放。
7. 更新携带预期修订号／版本。读后被别人改过时返回冲突并重预览，不采用静默最后写入覆盖。

食堂的营养证据仍可作为分析记录或修订来源存在；但**批准后的当前营养只有一个生效位置**。不允许食堂证据编辑器与主库编辑器分别维护两组当前数值。

### 3.3 食堂供应：在哪里、怎样卖一份

复用 `menu_items`，窗口与供应日程继续属于 `menu_services`：

| 字段语义 | 约束 |
|---|---|
| `id` / `serviceId` | 稳定供应 ID 与实际窗口关系，保留现有时段／星期语义 |
| `foodId` | 新增可空的权威主引用；链接后必须指向存在的主条目，删除策略为限制或显式处理，不级联误删 |
| 展示名 | 可与主食物名不同，如“招牌宫保鸡丁”；改展示名不影响主库身份 |
| `servingGrams` | 每一份实际克数，可空；有值须有限且大于零 |
| 份量来源与状态 | 建议来源：称重／用户填写／标签／AI 估计／历史未知；状态为已知、估计、未知。不能仅凭存了一个数字就变成可信 |
| 图片 | 该供应的实际图片，沿用应用私有副本和缺图降级；不是所有窗口共用的虚假实拍图 |
| 标签、配料 | 继续保留现有结构和来源。共用营养不等于窗口的实际配料或忌口证据必然相同 |
| 计算状态 | 由链接、完整营养、份量状态推导，不再另存可编辑的每份热量／三宏量 |

`MenuItemFoodMatches` 可继续存建议、拒绝和匹配历史；**唯一权威链接是供应的主引用**，确认候选须在同事务内落实它，不能出现“两条 confirmed 不知该用哪条”。

允许的四种可见状态：

| 状态 | 可以做什么 | 不能做什么 |
|---|---|---|
| 无主链接，待分析 | 展示供应、加照片、补营养或选择主食物 | 不显示“0 千卡”，不自动记餐或纳入营养预算 |
| 已链接，份量未知 | 显示每 100g 营养；用户可直接填本次实际克数记餐 | 不把“一份”换成 100g |
| 已链接，份量为估计 | 显示“约 X g／份”；用户明确接受估计后手动记餐并保留标志 | 不冒充称重；首版自动推荐默认不选这类供应 |
| 已链接，份量已知 | 按份派生营养、按份或克数记餐 | 不回写一份营养副本作为第二事实 |

### 3.4 兼容映射与迁移台账

增量增加持久化的旧实体映射／转换台账（可分表实现，不是新营养主库），至少表达：

- 唯一旧键：`legacyKind + legacyId`；对应主食物、可选供应和迁移时营养修订。
- 原始口径、原始份量、`basisAssumed`、来源／手改状态、原始内容指纹及保全资料。
- 转换规则版本、处理结果（已转换／待补全／冲突）、原因和关联证据。
- 同一旧键不能在重跑中创建第二个主食物；旧数据被实际修改后不能靠“已迁移”标记跳过冲突。

`[canteen-dish:id]` 仍指供应，不能偷换成主食物；`[dish:id]` 通过兼容映射保留旧每份语义。旧引用若指向的修订与当前主修订不同，应展示差异并重确认，不能悄悄按新值应用。

### 3.5 全局不变量

- 每个供应最多一个当前主引用；一个主条目可以被多个供应引用。
- 所有可计算营养都是每 100g，四项有限且非负；零可以是真实值，未知不能用零表示。
- 重量有限且大于零，份数有限且大于零；业务上限沿用并核对现有验证，不由提示词单独负责。
- 不强制热量必须严格等于三宏量 `4/4/9`，以免因标签舍入或口径差异误拒；显著异常可警示，禁止接受 NaN、无穷或负值。
- 当前主表投影与生效修订同事务一致；证据和未批准草稿不自动改当前营养。
- 名称仅做检索和候选提示；同一名称可对应多个有效 ID。
- 归档、删除、撤销、导入和恢复都必须维持外键、映射与来源完整性。

## 4. 份量与营养数学

### 4.1 唯一计算公式

```text
本次摄入营养 = 每100g营养 × 实际食用克数 ÷ 100
实际食用克数 = 本次份数 × 选中的供应每份克数

旧每份营养可转换的前提：每份重量有可信依据
每100g营养 = 每份营养 × 100 ÷ 每份克数
```

底层统一使用克数；份数、半份和通用份量在应用层解析后转克数。尽量复用 `NutritionMath` 的边界并补齐调用，不认为当前所有路径已经使用它。

**演算示例，非真实菜品营养承诺**：主食物为 180 千卡／100g。一窗口每份 200g，二窗口每份 250g，则分别为 360 与 450 千卡；二窗口半份为 125g、225 千卡。修改一窗口到 220g，只使其未来一份变为 396 千卡，不改二窗口或已有餐记录。

### 4.2 预填、估计与未知

- 直接从主食物记餐：可提供通用份量／最近使用量作为可编辑预填，但界面明确标成建议；默认 100g 如仍保留，只能表达“本次输入框的 100g”，不能声称是一份重量。
- 从供应按份记餐：必须使用该供应的份量。重量未知时要求补本次实际克数，或先完善供应；不借用另一窗口或主食物通用份量静默替代。
- 照片和 AI 可提供“估计约 200g”的建议；用户接受后仍是估计，来源不升级成称重。
- 修改本次食用量不反向改供应份量；明确点“修改该窗口每份重量”才更新供应。
- 只有可信每份克数才允许把旧每份营养归一成主库事实。单纯接受一个历史猜测不证明原值可换算，应补证据或重新分析。

### 4.3 记餐快照

沿用并补齐 `MealRepository` 的快照契约：主食物 ID、可选供应 ID、当时修订／来源、本次克数、可选份数与份量依据、最终营养值。历史名称、实际重量与营养数值保留原样。

旧每份餐、手工餐和仅有快照的记录继续可读，不强制找到新主食物才能显示。修改历史餐时区分“按原快照调整量”和“主动换用最新营养”，后者须预览并明确确认。

所有仍可达路径都要纳入：统一记餐编辑器、供应详情记餐、旧菜品记餐适配、AI `meal.create`、推荐应用及餐记录编辑。不能只改 `CatalogResolver` 就宣称数学已收敛。

## 5. 用户操作闭环

### 5.1 统一食物库

列表统一显示食材和成品菜，不要求用户理解 `food`、`dish` 两种内部表。搜索可按既有来源／分类过滤，但所有入口共享同一身份查询。

```text
新建食物 → 名称／品牌／做法说明 → 每100g营养及来源 → 保存到食物库
保存结果：已保存到食物库。可用于记餐或添加到食堂窗口。
```

营养资料只有每份时，允许输入每份营养＋可信每份克数，界面预览换算后的每 100g，再保存。没有重量时不能直接当成每 100g，进入补全流程。

内置／导入条目默认“复制为我的版本”以保留原始来源；用户自建共享条目修改时进入影响范围预览。归档筛选、别名和重复候选不要替用户自动合并。

### 5.2 食堂新建供应

```text
选择窗口 → 搜索统一食物库
  ├─ 选已有主食物
  └─ 未找到：在当前流程中新建主食物／先建待分析供应
→ 补每份克数及来源、实拍图、展示名、供应信息
→ 确认 → 保存供应
```

- 选择主食物后立即展示“每 100g”事实与来源；输入每份克数后派生“一份约多少千卡”。
- 图片可选，营养与照片不绑定；缺图用占位，不伪造图片。
- “保存供应”不记成吃过。额外选择“保存并记一份”才生成餐记录，并预览日期与克数。
- 同流程新建主食物＋供应，提交前取消不遗留半成品写入；单独“仅保存到食物库”是另一明确提交动作。
- 待分析供应可先建，不要求为了挂窗录假营养。

### 5.3 修改共享数据

供应详情把两种修改分开：

1. **修改窗口信息**：每份重量、展示名、照片、时段等，只影响该供应。
2. **修改营养／重新分析**：默认“建立此窗口的做法版本”，新建／修订该变体并改引用；可显式选择“更新共享食物营养”，先显示受影响的供应数量及名称，并说明历史餐不变。

如果该主食物只被当前供应引用且为用户自建，也仍展示修改范围，不能通过当前引用数猜测长期身份。并发修改产生版本冲突时重取数据、重预览。

### 5.4 删除、停用与原始资料

- 删除窗口供应：不删主食物、不删历史餐。若主食物由本流程创建但已提交，删除供应也不顺手清空它。
- 主食物仍被引用：默认归档；现有供应详情能解释“已归档，需选择替代条目”，不进入自动推荐，新挂窗不能选用。可在修复前按原完整修订及明确克数手动记录，不能隐式替换为同名食物。
- 未被引用的主食物也需走显式删除／撤销，不能在“清理重复”时批量按名字删。
- 旧图片、点评、营养原值和待补全原因在详情“原始资料”可查看。保存在 JSON 中但界面永远读不到，不算保全完成。

### 5.5 写入与图片失败

同一次明确的“建库＋挂窗＋记餐”使用依赖链和单个数据库事务，前一步失败不继续；独立意图则分别提交和分别回执。所有写入使用稳定请求键防重试重复。

图片文件与数据库不是同一种事务：先准备应用私有副本，再提交数据库；失败仅清理本次拥有且未被引用的临时副本，不能误删其他供应共享文件。缺图不阻断已合法保存的营养读取；恢复时路径存在性与文件内容另行验证。

## 6. AI、搜索和推荐的适配

### 6.1 三种意图必须分开

| 用户说法 | 目标动作 | 成功回执示例 |
|---|---|---|
| “存一个宫保鸡丁到库里” | 创建／选择统一主食物 | “已保存到食物库；尚未添加到窗口，也未记餐。” |
| “把这道菜放到一窗口，一份200g” | 解析主食物＋建立供应 | “已添加到一窗口：宫保鸡丁，每份200g；未记餐。” |
| “我吃了一窗口半份宫保鸡丁” | 解析供应、换算克数、创建餐快照 | “已记入本次餐记录：半份，100g。”（仅当该供应确为200g／份） |
| “新建、挂一窗口，并记一份” | 有序执行三步 | 每一步独立说明，卡片每个食物下方显示最终去向和克数 |

“生成应用卡片”继续是将用户意图编译成可执行动作，不因主库统一而自动执行聊天建议。取消、重试、去重、15 秒幂等及迟到事件保护继续回归。

### 6.2 命令契约与旧信封

下表是**未来改造要求**，不是当前协议已支持的新参数：

| 命令／能力 | 改造规则 |
|---|---|
| `food.create` | 唯一新建主营养入口，明确每 100g；同名命中只给候选，不能仅因唯一同名就认作同一做法或直接覆盖 |
| `dish.upsert` | 新编译不再生成独立每份菜品写入；旧信封仍按旧每份语义解码，经兼容服务预览安全转换，缺重量时提示补全而非改标签写入 |
| `canteen.dish.create` | 新契约以明确 `foodId`／受控结果引用挂窗；可另建待分析供应。旧 `nutritionFrom` 分支须由版本适配解释，不能让新旧参数含义漂移 |
| `canteen.dish.nutrition` | 归一为每 100g 分析建议，批准后调用主营养修订／窗口变体服务；不继续直接维护食堂当前营养副本 |
| `meal.create` | 底层继续克数。供应份数先由应用层解析为实际克数，再提交；仅在 prompt 添加 `unit` 不会实现份数支持 |
| 组合依赖 | 主食物创建返回稳定 ID，供应创建使用该 ID，记餐再使用供应 ID；使用受验证的结构化结果引用，不按名字拼接 |

当前 `canteen.dish.create` 收到 `nutritionFrom=ai` 不等于创建函数已经实际调用营养分析；后续须把“先建待分析”与“分析后建库挂窗”的真实执行分开测试。

为新信封明确引入契约版本，缺版本按旧协议。原始信封落库并在重启时重解析，因此必须：

- registry、严格参数校验、执行器、持久化反序列化及 UI 预览一起升级；未知字段仍拒绝，不通过放宽任意参数解决兼容。
- 已应用的旧卡片仅展示历史，不因重解析再次执行。
- 未应用的旧卡片重新应用前校验 ID、版本、份量和来源；无法安全转换显示“需要重新生成／补全份量”，原文和原始载荷保留。
- 旧 `[dish:]` 不以新每 100g 语义直接运行。链接已删除或有歧义时停止对应依赖链，不能用第一个同名结果替代。
- 改造不能清掉 dismissed 状态、应用结果、去重信息或原先的日期确认。

### 6.3 数字接地与快照

- 新的每份克数、份数、每 100g 值都纳入显式数字策略；未配置字段 fail-closed，不只改提示词。
- 保留既有 `food.create` 营养预览例外的明确边界，不把它扩大成随意发明重量、窗口、日期或直接记餐的通行证。
- 结构化食堂／标签／用户输入数据可以作为来源；AI 估算必须有估算来源并按卡片流程明确应用，禁止把旧假设 100g 包装成事实。
- 快照输出主食物 ID、供应 ID、窗口、每 100g 营养／修订、份量状态、每份克数及来源、是否已挂窗；不再用两个同名段落暗示两个互不相通的库。
- 拿到新 ID 后立即失效相关搜索、快照与派生缓存。复用既有索引协调能力，不能靠重启才可见。

重点落点：`chat_edit_executor.dart`、命令模型／registry、`chat_edit_number_grounding.dart`、`chat_edit_context_loader.dart`、持久化消息仓库和卡片协调器。现有按名称串联 `food.create→meal.create` 的特殊逻辑不能直接承担新的三步依赖。

### 6.4 搜索与索引

三个入口共用主库检索及身份结果：

1. 食物库：查主食物，按既有分类／来源筛选。
2. 记餐：主食物结果用于克数输入；真实供应结果用于份数输入，明确窗口和份量，不能把二者作为无法辨别的重复行。
3. 食堂新建供应：查同一主库，选中后建立供应关系。

中文别名、分片／扩展目录和当前索引策略继续可用；外部分片候选须按既有规则物化为稳定主食物后才能建正式链接，不能保存临时搜索结果编号。语义匹配只推荐，不决定实体相等。

### 6.5 两条推荐链统一口径

当前本地每日推荐按 `DishRecord.kcal` 每份比较预算，AI“换一套”路径可能按食堂每 100g 值并构造假设 100g；两条都必须改。

目标统一使用：**可供应窗口＋主食物生效营养＋有依据的该供应份量**。第一版自动推荐只选完整营养且份量已知的供应；待分析、份量未知或只有历史假设的项排除并解释原因，不自动补 100g。

预算比较、展示“一份多少”、推荐应用后的克数和记餐结果必须来自同一份解析结果。同名不同窗口保留各自供应 ID；换一套不能破坏时段、星期、忌口等既有约束。主修订变化后推荐缓存失效，历史已应用的餐不变。

## 7. 旧数据迁移与旧备份恢复

### 7.1 先审计，后转换

当前 schema 为 30。schema 28 曾对缺失份量填 `100` 并标 `basisAssumed=true`，代码锚点为 `lib/data/database/app_database.dart:640`。因此：

- `servingGrams == 100` 不证明真实称重。
- `basisAssumed == false` 也不能单独证明旧来源可靠，要结合原始版本、来源和修改记录。
- 读取迁移原始行及原始备份字段，不经过会丢 `nutritionBasis` 的 `DishRecord` 映射，也不先把缺失字段补默认值再判断。

P0 做只读盘点：记录数、来源、口径、份量状态、手改、重复来源、悬空 ID、非法／不完整营养、媒体路径和历史餐快照。盘点不按名字删改数据。

### 7.2 分类矩阵

下表可能交叉命中。先检查手改／冲突和原始口径，再决定转换；优先保全有证据的原值，不以“来源来自食堂”覆盖用户修改。

| 类型 | 处理 | 禁止行为 |
|---|---|---|
| A. 原 `foods` 完整每 100g | 保留原 ID、分类与来源，建立基线修订 | 重建 ID，造成现有引用失联 |
| B. 明确原每 100g 的旧条目 | 四项合法且证据一致时原值归一；保留原口径证明 | 仅因新字段默认值写着 per100g 就认定 |
| C. 每份营养＋可信每份克数 | 按公式换算四项和单位明确的微量值，保留原值／克数／证据 | 对未知或非有限重量换算 |
| D. 食堂有可靠原每 100g 证据 | 可据此建立主修订并链接供应；保全旧每份副本及差异 | 反过来用假设100g副本覆盖原证据 |
| E. 历史假设100g／未知每份重量 | 原值、每份口径原样进入待补全兼容区；可显示和补资料 | 把“每份300千卡”当“每100g300千卡” |
| F. `userEdited=true` 或手改痕迹 | 独立审视；可换算则保留用户版本，必要时成为变体；不可则待补全 | 自动同步或迁移覆盖用户值 |
| G. 多条副本同来源 | 只有源 ID、口径、修订及数值证据一致才复用；其余保留多个版本／冲突 | 只按来源键或同名强合并 |
| H. 悬空来源／多重确认匹配 | 保留原条目和原因；可安全换算则独立建主条目，否则待补全 | 猜某个窗口、第一条同名或伪造外键 |
| I. 缺营养、仅有区间、非法值 | 原始资料保全；进入待分析／待补全，不进入可计算主库 | 填零、取区间中点或吞异常跳过 |

旧独立菜品没有实际窗口时，只建立可转换的主条目／通用份量资料，不凭空造“默认窗口”。旧图片、点评和扩展营养须保全且可查看，不能要求必须挂窗才能找回。

### 7.3 转换机制与对账

1. **迁移前保全**：先验证可恢复备份和匹配旧版本，确认可用空间；没有可验证的安全副本不执行用户数据迁移。
2. **纯规则层**：输入原始记录＋来源上下文，输出归一值、保全资料、映射或待补全原因。规则版本固定，便于夹具独立测试。
3. **事务层**：写主条目、修订、供应链接、映射和台账，在一致性事务内完成；非预期错误抛出并回滚，不吞错误继续造半条关系。
4. **幂等**：旧键＋源指纹＋转换版本控制重入，不对已换算值再次除份量。重跑结果主 ID、修订与值不变。
5. **冲突保留**：可预期的数据缺失落入待补全台账，仍计入总数；结构损坏、未知规则或对账不平属于失败，不是“已跳过”。
6. **逐条对账**：每个旧实体必须有结果；已转换／待补全／冲突的旧键不重不漏。新建主条目数量可以因有证据复用而减少，不能只比较新旧行数宣称无丢失。
7. **快照保护**：迁移前后比对历史餐日期、名称、实际克数和营养快照；来源 ID 的兼容映射不改变这些值。
8. **数值精度**：保留计算精度，只在显示层舍入；转换夹具以约定浮点容差对账，重复执行不能产生漂移。

旧兼容记录可以继续按原快照／原单位供用户查看、预览或补全；不能回到独立可写营养库。无法可靠解释克数的旧引用，不自动用于新的按克记餐或自动推荐。

### 7.4 数据库升级与 `.lfb` 恢复是两个入口

数据库 `onUpgrade` 不能覆盖旧 `.lfb` 导入路径。恢复方案必须复用同一版本化规则：

```text
旧数据库升级 ── 原始行适配 ──┐
                            ├─ 归一化规则 → 主库／供应／映射／台账 → 同一校验
旧.lfb解析 ── 原始载荷适配 ──┘
```

- 备份先解密、校验版本／结构／大小，再恢复；保留原载荷中“字段缺失”和“显式100g”的区别，不能被注册表默认值抹平。
- 恢复写表与归一转换处于受控恢复事务；失败保留恢复前数据库，不先清空现有数据再尝试修复。
- 新格式完整备份须覆盖生效修订、主引用、份量来源、旧映射和保全资料；数据库 schema 版本与备份载荷版本分别管理。
- 同一旧夹具经直接升级和经 `.lfb` 恢复，业务结果及待补全原因等价；依流程生成的时间等非业务元数据不能掩盖营养差异。
- 图片路径字符串不等于图片字节。先核对当前备份媒体能力；要承诺跨设备恢复，须纳入受校验的媒体内容及引用重定位，并实际验证。未覆盖时界面／文档明确图片缺失边界，不能写“完整恢复了照片”。

当前 CSV 是十列内容交换，不能保留完整稳定 ID、供应链接、修订和媒体。CSV 导出再导入可以按现有名称／品牌提示重复，但不承担实体身份恢复；用户需要完整关系时走 `.lfb`。

### 7.5 回滚和旧路径退役

- 结构迁移失败：事务回滚，保留原库，输出可解释错误，禁止继续启动一半新模型。
- 业务数据无法归一：该行有明确待补全结果，其他转换能否提交取决于整体对账与外键校验，不把它记作完整成功。
- 上线后回退：恢复**迁移前验证过的备份＋匹配旧应用版本**，告知迁移后新增数据的保全／导出方案；不承诺旧应用能直接打开新 schema。
- 功能开关用于开发切换和诊断，不能在迁移后简单关开关就重新启用旧可写营养副本。
- 首个收敛版本保留旧原始数据和只读兼容；删除旧表须另有依赖检查、保全与恢复测试依据。旧 UI／运行链退役不等于删掉旧备份解析器和 ID 映射。
