### 6d 卡片关联的硬要求（别再做成半条）

用户原话：
> 「我点击鸡蛋水煮的应用的时候，应该弹窗提示是否应用创建食材鸡蛋水煮，
> 我选择确认后又可以继续应用该早餐添加，而不是我点击应用后，因为下边的卡片
> 没有点击应用，导致食物库没有鸡蛋水煮，从而添加失败。」

必须同时满足：

1. 缺食材 **且** 同卡内有对应 `food.create` ⇒ **弹确认**（Key `chat-edit-dependency-confirm`）；
2. 确认 ⇒ **先应用那条创建，再重试记餐**，两条都变已应用；
3. 拒绝 ⇒ 记餐失败并如实说明，**不许留下半条记录**（食物库不许有那条食材）；
4. 缺食材 **但同卡无创建** ⇒ 沿用既有「新建食材」修复按钮，**不弹确认**；
5. 食材已存在 ⇒ **什么都不弹**（不能每次记餐都问）；
6. 一次有多条缺失 ⇒ **一次性列全**，不逐条连环弹；
7. 第一次写（创建）失败 ⇒ **不重试**记餐，如实报错；重试前**重新读一次食物库**（防并发重复建）。

### §19 合并板块的硬要求（2026-10-25 用户新增）

用户原话：
> 「新建食材和新建菜品记录要合并，不要分开两个板块，如果已经有的食材，点击应用后
> 即可计入，如果没有，我点击应用后后就先新建再计入」

必须满足：
1. **当 `food.create` 服务于本卡某餐时**（该餐 items 引用了这个新食材）⇒
   它**不再是独立板块**，而是那个餐的**子条目**，带「新建」徽标；
2. 此时**不出现** `chat-edit-group-*-food` 这个组头；
3. **纯新建食材**（用户只说「加一个叫麻辣烫的食材」、没有任何餐引用它）⇒
   **仍保留独立「新建食材」板块**——不能为合并把它也吞掉；
4. 合并后点「应用本组」⇒ **食材创建 + 记餐一次完成**（与 6d 的执行顺序串联）。

§19 与 §6d 是同一件事的两面：**6d 管执行顺序，19 管视觉呈现**。
只做 6d 不做 19，用户仍会觉得「为什么要分两块」；只做 19 不做 6d，点一次仍会失败。
**建议同批做。**

### §20 记录页卡片的硬要求（2026-10-25 用户新增）

用户原话：
> 「每一餐的卡片上，食物都放一起，不要按照时间分开，而且三宏量有的根本看不见，
> 被挡住了，变成省略号了，可以不显示三宏量，只显示热量」

必须满足：
1. **卡面不再出现「蛋白质 X · 碳水 Y · 脂肪 Z」**那串文字；
   根因是 `meal_record_card.dart:151` 的 `maxLines:1 + ellipsis` 且被 `Flexible` 挤压；
2. **热量保留在卡头大号位**（`${nutrition.kcal.round()}` + `kcal`）；
3. 底行只留：来源徽标 + 备注 + 管理菜单（空间宽松后不许再有「…」）；
4. 320dp × 2.0× 下**不溢出、不出省略号**；
5. 三宏量若想保留可访问性 ⇒ 放**读屏语义**或**编辑弹层**里，视觉不占位。

> **「不要按时间分开」已确认（2026-10-25）**：用户要的是
> **去掉卡头时间** + **同名餐次多条记录合并成一张卡**（「午餐就都放一起，
> 不要因为我后边记的就分开显示」）。
> 根因：`nutrition_record_slot_grouping.dart:236` 用
> `for (var index = 0; index < meals.length; index++) MealRecordCard(...)`
> —— **每条 meal 记录一张卡**，所以记两次午餐就出现两张「午餐」卡。
>
> **实现取向（推荐）**：卡内**按原记录分组但用极淡分隔线**，视觉上是一张卡、
> 食物都在一起；编辑/删除仍按**原 meal.id** 定位（不引入"合并后如何拆开"的新问题）。

### §9 热量与营养推荐按区间（用户硬要求）

用户原话：
> 「要区间的方案，另外你的热量目标和营养推荐都要根据区间来设计，**数据一定要准，
> 推荐一定要有依据**。」

**先说清楚：算法本来就有依据，不需要重写**（`nutrition_target_calculator.dart`）：
Mifflin–St Jeor BMR → ×活动系数 TDEE → 目标调整（减脂 0.85 / 维持 1.0 / 增肌 1.08）
→ 热量区间 = 中心 ×0.95～1.05 → 蛋白按 **g/kg 区间**（减脂 1.6–2.0 等）→
脂肪 `体重×0.7～1.0` → 碳水由热量反算 4/4/9 → **成人安全下限（女 1200/男 1500）越界直接抛错**。
**要改的是"没显示出来"和"四处口径不一致"，不是算法。**

必须满足：
1. **四处统一为区间**：
   - 仪表盘热量卡：卡头 `1,700 – 1,900`（不再单个中点）；「还可摄入」也是区间；
   - 菜单页三餐推荐：不再只用 `calorieMaxKcal`；
   - 「今天还剩多少」chip：**已经**是区间，保持；
   - 菜品卡进度条分母：**保持 `calorieMaxKcal`**（进度条必须有确定分母，取上限是保守且
     与"不超上限"一致），但**在代码注释写明这是有意取舍**。
2. **三宏量块显示区间**：`90–130 g` / `180–260 g` / `40–70 g`（三色点沿用橙/黄/紫）。
3. **进度环改区间带**：绿带 = 目标区间，指针 = 当前位置；超上界时带变暖色 + 标「超上限 X」。
4. **卡上标依据（一行）**：如「目标 1,700–1,900（Mifflin–St Jeor × 活动系数，减脂 −15%）」。
5. **禁止凭空造数**：推荐一餐的热量目标必须由 `target.min/max − 已摄入` 算出；
   算不出来就说「数据不足」，**不许给假数字或硬编码**。
6. 显示的数字与 `NutritionTargetCalculator.calculate()` 输出**逐字相等**（写单测钉住）。

设计稿：`calorie-target-range-vs-single.html`（B 方案已由用户选定）。
