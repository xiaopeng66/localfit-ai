## 1. §1 卡片关联（6d）——**本轮最重要**

### 用户原话

> 「当我计入的食材是新建食材的时候，希望能把两个卡片关联一下，比如我点击鸡蛋水煮的
> 应用的时候，应该弹窗提示是否应用创建食材鸡蛋水煮，我选择确认后又可以继续应用该
> 早餐添加，而不是我点击应用后，因为下边的卡片没有点击应用，导致食物库没有鸡蛋水煮，
> 从而添加失败。」

### 现状与根因

一张编辑卡里，「记一餐」与「新建食材」在**两个不同的组**，组级应用互相独立：

- `chat_edit_card.dart` 按 `_EditGroupKind`（meal / food / other）分组，每组一个「应用本组」；
- 用户只点「记一餐」那一组 ⇒ `food.create` 没执行 ⇒ 食物库里没有「鸡蛋水煮」；
- 应用到 `meal.create` 时，`chat_edit_executor.dart:1225` 报
  「找不到食材「X」。没有的食材要先用 food.create 创建。」

**用户要的是**：检测到这种依赖，**提示并串起来做**，而不是让他自己去点另一组。

### 方案

在 `meal.create` 应用前做**依赖检查**（放在 controller 的 `applyEdits` 里，不是 executor——
executor 只认识单条命令，看不到同卡其他行）：

1. 取该 `meal.create` 的 `items[].food`；
2. 逐个查食物库（`FoodRepository.searchExact`）；
3. **缺失**且**同卡内存在对应 `food.create`（按 name 匹配）** ⇒
   - 弹确认：「要先创建食材「鸡蛋水煮」吗？创建后就能记这一餐。」
   - 确认 ⇒ **先应用那条 `food.create`**，再重试 `meal.create`（两条都变已应用）；
   - 拒绝 ⇒ 该行失败，原因如实（沿用现有失败文案）。
4. 缺失但同卡**没有**对应创建 ⇒ 沿用现有「新建食材」修复按钮（`ChatEditRepair`），不改。

### 验收判据（RED 先行）

| 判据 | 期望 |
|---|---|
| 缺食材 + 同卡有创建 | 必须弹确认（新 Key `chat-edit-dependency-confirm`） |
| 点确认 | **两条都应用成功**；食物库真的有「X」；餐记录里有它 |
| 点拒绝 | `meal.create` 行失败，原因说明缺什么；**不留半条记录** |
| 缺食材 + 同卡无创建 | 不弹确认，走既有修复按钮 |
| 食材已存在 | 不弹任何东西（不能每次记餐都问一遍） |
| 一次卡里多条缺失 | 一次性列全，**不逐条弹**（避免连环弹窗） |

### 风险与回滚

- **会连续写两次库**：必须保证第一条失败时**不写任何东西**（`food.create` 失败 ⇒ 不重试 meal，
  如实报错）；重试前**重新读一次食物库**（避免并发插入导致重复建食材）。
- 回滚：单独 commit，可 revert 本条而不动其它。

## 3. §3 chip「按文字长度调整大小」（8c 未完成的部分）

### 现状

- ✅ 换行已修（`softWrap: false`）
- ✅ 水平居中已修（`textAlign: center`）
- ❌ **「根据文字长度来调整」未做**：三枚 chip 仍是 `Expanded` **等分**（各占 1/3）。

### 为什么当时没做（如实）

我第一版就是「按内容宽度 + `Wrap` 居中」——**320dp × 2.0× 下溢出 170px**
（`Wrap` 不会收缩子项），而且我的批量替换**误改了输入框那一行**导致 80 条测试失败。
退回等分 + `FittedBox` 是当时风险最低的选择。

### 现在的方案

用 `LayoutBuilder` 判可用宽度：
- **够宽**（≥ 三枚自然宽之和 + 间距）⇒ 按内容宽度排、居中（用户要的效果）；
- **不够** ⇒ 回落等分（保证不溢出）。

判据：390dp 下三枚宽度**不相等**且整行居中；320dp × 2.0× 下**不溢出**。

## 9. §9 热量目标 + 三宏量区间显示（1）

- **现状**：热量卡只显示单值「目标 1,844 kcal」；`daily_targets` 表里
  `calorie_min/max`、`protein_min/max` 等**区间数据是有的**，只是没上屏。
- **口径已出设计稿，等用户选**（2026-10-25）：`calorie-target-range-vs-single.html`
  （A 单值 vs B 区间，含三宏量块与区间进度条的两种画法）。
  **推荐 B（区间）+ 保留区间进度带**；若嫌数字长可选 A，但要加一行小字
  「目标是 1,700–1,900 的区间」，至少不撒谎。
  区间更忠实于目标模型（它是范围不是点值），但与「已摄入/剩余」的单值算式并列时，
  用户可能困惑「剩余是按哪个减的」。
- **方案 A（推荐）**：目标行显示区间「目标 1,700–1,900 kcal」，剩余仍按区间算并标注

## 12. §12 版本号 / 在线更新 / 帮助 / 反馈（17b–17e）

### 12.1 版本号「未知」——**根因已查明，一行搞定**

`main.dart:662` 用 `String.fromEnvironment('APP_VERSION')` 读构建期变量，
而 `main.dart:663` 在**没注入时返回 null** ⇒ `settings_page.dart:1351` 显示「版本未知」。

**我构建 APK 时没传 `--dart-define=APP_VERSION=`** —— 这是我的疏漏。

两种修法：
- **A（最小）**：构建命令加 `--dart-define=APP_VERSION=4073`（每次构建都要记得传）；
- **B（推荐）**：用 `package_info_plus` 读 pubspec 的 version——**但那是新增第三方依赖**，
  与既有约束冲突。**替代**：把 `--dart-define` 写进一个构建脚本（`tool/build_release.bat`），
  从 `pubspec.yaml` 的 version 自动取值，**不新增依赖也不会忘**。

### 12.2 在线更新（点击检查更新并安装）

**基础已就绪**：Release `v4073` 已建，三个 APK 匿名可下载（实测 302→200）。

实现方案：
1. `GET https://api.github.com/repos/xiaopeng66/localfit-ai/releases/latest`
   （或读 `releases/download/v<vc>/...`）拿到最新 `tag_name` → 解析出 versionCode；
2. 与本地 `APP_VERSION` 比对 → 有新版则显示「发现新版本 vXXXX」+「下载安装」；
3. 下载走 `dio`（已有依赖）→ 存到应用私有目录 → `Intent.ACTION_VIEW` 触发系统安装
   （需 `REQUEST_INSTALL_PACKAGES` 权限 + `FileProvider`）。

**风险**：安装包权限与 FileProvider 配置要动 `AndroidManifest.xml` 与 `res/xml/`，
属**系统集成级改动**，必须真机/模拟器验证安装能起来。**建议单独立一轮做**。

## 6.5 §19 新建食材与记一餐合并（2026-10-25 用户新增）

### 用户原话

> 「新建食材和新建菜品记录要合并，不要分开两个板块，如果已经有的食材，点击应用后
> 即可计入，如果没有，我点击应用后就先新建再计入」

### 现状与根因

`chat_edit_card.dart:766`：

```dart
enum _EditGroupKind {
  meal('记一餐'),
  food('新建食材'),     // ← 独立板块
  other('其他修改'),
}
```

`_groups` 按 `_EditGroupKind.values` 顺序分组，各组独立渲染、各自一个「应用本组」。
于是**同一次记录拆成两个板块**：上面「记一餐（米饭/鸡胸肉）」，下面「新建食材（鸡蛋水煮）」。
用户要先点下面那个组，再点上面那个组——正是 §1/6d 那条依赖问题的**视觉根源**。

### 方案

**把「新建食材」并进「记一餐」板块**，作为该餐的**子条目**，而不是独立板块：

- 一条 `meal.create` 的 items 里，某个食物在库里不存在、而同卡有对应 `food.create` ⇒
  把它渲染成**该餐下的一个子条目**，带「将新建」标记（如小徽标「新建」）；
- 不再渲染独立的「新建食材」组；
- 如果 `food.create` **不与任何 meal 相关联**（用户单纯说「加一个叫麻辣烫的食材」）⇒
  **仍保留独立分组**（那种情况确实不是"记一餐"的一部分）。

### 与 §6d 的关系（**必须一起做**）

§6d（卡片关联）解决的是**执行顺序**（先建再记）；§19 解决的是**视觉呈现**（合成一块）。
两条其实是同一件事的两面——**只有合并后的卡片，用户才会觉得「点一次应用就够了」**。

实现顺序：先 6d（执行层能串起来），再 19（视觉合并）。或同一批做。

### 验收判据

| 判据 | 期望 |
|---|---|
| 记一餐 + 其食物需要新建 | **只有一个板块**，标题是「记一餐」；新建的食材作为该餐子条目出现 |
| 子条目标记 | 该子条目带「新建」徽标（Key `chat-edit-subitem-new-<c>-<i>-<j>`） |
| 组数 | `chat-edit-group-*-food` **不出现**（当且仅当该 food.create 服务于本卡某餐） |
| 纯新建食材（无 meal） | 仍出现「新建食材」板块（不能为了合并把它也吞掉） |
| 应用一次 | 点「应用本组」⇒ **食材创建 + 记餐一次完成**（与 6d 联动） |

## 6.6 §20 记录页每餐卡片：食物合并 + 只显示热量（2026-10-25 用户新增）

### 用户原话

> 「记录里，每一餐的卡片上，食物都放一起，不要按照时间分开，而且三宏量有的根本
> 看不见，被挡住了，变成省略号了，可以不显示三宏量，只显示热量」

### 现状与根因（两件不同的事）

**(a) 三宏量被省略号挡住 —— 根因明确**

`meal_record_card.dart:151`：

```dart
Flexible(                                    // ← 可以无限压缩
  child: Text(
    '蛋白质 ${..}g · 碳水 ${..}g · 脂肪 ${..}g',
    maxLines: 1,
    overflow: TextOverflow.ellipsis,          // ← 挤不下就「…」
  ),
),
const SizedBox(width: 8),
Expanded(child: Row(...))                     // ← 右边还吃掉一半宽度
```

左边 `Flexible` + 右边 `Expanded` ⇒ 左半被压到很窄 ⇒ 三宏量必然变省略号。
**这不是字体大小问题，是布局抢宽度。**

**(b) 「按时间分开」—— ✅ 用户已确认（2026-10-25）**

用户原话：「**去掉时间显示，午餐就都放一起，不要因为我后边记的就分开显示**」。

⇒ 两件事都要做：
1. **去掉卡头的时间**（`_clockLabel(meal.eatenAt)`）；
2. **同名餐次的多条记录合并成一张卡**——用户后边再记一次午餐，不该多出一张卡，
   而是并进已有的「午餐」卡里，食物列在一起。

**根因（已核实）**：`nutrition_record_slot_grouping.dart:236` 是
```dart
for (var index = 0; index < meals.length; index++)
  EntranceItem(child: MealRecordCard(meal: meals[index], ...))
```
**每条 meal 记录渲染一张卡**。所以今天记两次午餐 = 两张「午餐」卡（各自带时间）。

### 方案（(a) 立即做；(b) 待确认）

**(a) 只显示热量，去掉三宏量行**
- 删除底行那串「蛋白质/碳水/脂肪」；
- 保留卡头右侧的大数字 kcal（已经是「大数字 + kcal」）；
- 底行只留：**来源徽标 + 备注 + 管理菜单**（空间一下子宽松）；
- 若担心信息丢失：**把三宏量移进「编辑」弹层**（那里本来就有完整营养），
  或作为 `tooltip`/读屏语义保留（视觉不占位）。

**(b) 同名餐次合并 + 去时间**（用户已确认要做）

1. **槽位卡内按 `(date, slot)` 聚合**：`meals` 已是同一 `(date, slot)` 的列表
   （分组层已按 slot 分好），所以只需在**渲染层**把多条记录的食物**拉平合并**成一张卡；
2. **卡头去掉 `_clockLabel(meal.eatenAt)`**，只留餐次名（「午餐」）；
3. **合计**：热量与三宏量按合并后的全部食物累加；
4. **操作仍按原记录**：编辑/删除要能定位到**具体那条 meal 记录**——
   * 若合并成一张卡，"编辑"要能选改哪一条 ⇒ 卡内每行（每个食物）给来源记录的入口，
     或管理菜单列「本次记录（HH:mm）」多条；
   * **更简单且安全**：卡内**按原记录分组显示但用极淡的分隔**，视觉上仍是一张卡、
     食物都在一起，而编辑/删除保持按记录粒度。**推荐这个**（改动小、不引入
     "合并后如何拆开"的新问题）。
5. **多选模式**仍需能勾选到具体记录（`selectedIds` 是按 meal.id 的）。

### 验收判据

| 判据 | 期望 |
|---|---|
| 三宏量 | 卡面**不再出现**「蛋白质 … 碳水 …」；`meal-totals-<id>` 这个 Key 随之退役（写进证据） |
| 热量 | 卡头 kcal 仍在大号位（`${nutrition.kcal.round()}` + `kcal`） |
| 省略号 | 底行**没有** `overflow: ellipsis` 的宏量文本（`expect(find.textContaining('蛋白质'), findsNothing)`） |
| 320dp × 2.0× | 不溢出、不出现「…」 |
| 读屏 | 语义里仍能读到三宏量（若保留 tooltip/semantics 方案） |
