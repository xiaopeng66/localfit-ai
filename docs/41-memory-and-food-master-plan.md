## 0. 一页速览

**目标**：让 AI 真正「记得住」、让菜品/食物「找得到、算得准」，并且三套系统互相咬合、整体更快。

**三条线**
- **S11 记忆**：v1/v1.1 **已落地**（表 `ai_memories`、命令 37 条、快照两段、管理页、提炼、备份兼容）。
- **S13 食物数据**：四层模型 + 份量口径 + 显式链接 + 配料/过敏原 + 同步（待开工）。
- **S12 检索**：端上向量 + RRF 混合 + 标签/口味 + 索引治理。**2026-10-19 已启用**（用户「开」）：P0 稳态复测后 maxLen 32 + 前缀 B 两条门槛都过 ⇒ 模型随包（`assets/models/`）、`SemanticRuntime` 接线菜品检索与记忆注入；**未做**：worker isolate（首次加载有一次秒级卡顿）。
- **S14 时间语义（2026-10-19 用户授权追加）**：`ai_memories` +`validFrom`/`validTo`，
  支持「某条目从何时成立、到何时失效」与「当时是什么」查询（G23）；schema 29。

**顺序**：S13-P1（界面）→ S13-P2（schema 28）→ S12（索引与检索）；**S12-P0 评测与 P1 并行**。
理由：向量必须建在正确的份量口径与身份链接上。

**已锁定的关键选择**：端上 `bge-small-zh-v1.5` int8（512 维，≈24MB）；在线 embeddings 只作评测基线；
Drift 存向量 + 暴力余弦（sqlite-vec 与 SQLCipher/sqlite3 2.9.4 不兼容）；融合用 RRF；硬/软过滤分离。

## 4. 统一架构（三层系统 + 四层数据）

```
                       ┌──────────── 记忆系统 (S11 已有 + 本文升级) ────────────┐
                       │ 捕获：命令 / 手写 / 提炼 / 会话结束提议 / 会话级临时记忆 │
                       │ 治理：去重(向量) / 合并提议 / superseded / 过期 / 晋升约束 │
                       │ 注入：query-aware + 门控 + MMR + 三档预算 + 实体链接     │
                       └───────────────┬──────────────────────────────────────┘
                                       │ 写入/读取
   ┌──────────────── 检索系统 (S12) ────▼───────────────────────────────────┐
   │ 嵌入(端上 bge-small-zh) → 索引(embedding_index: memory/dish/food/menu) │
   │ 硬过滤(过敏/营业/今日菜单) + 向量 + bigram 关键词 + 标签 → RRF → MMR    │
   └───────────────┬──────────────────────────────────────────────────────┘
                   │ 供查询
   ┌───────────────▼──── 食物/菜品系统 (S13) ──────────────────────────────┐
   │ 食物库 foods = 每100g 事实   │ 食堂菜 menu_items = 供应事实 + 配料/标签 │
   │ 菜品库 dish_library = 份量模板 │ 餐记录 meal_items = 不可变快照          │
   │ 链接：menu_item_food_matches / dish_library.source* / 配料 / 偏好实体    │
   └──────────────────────────────────────────────────────────────────────┘
```

**四条铁律**：① 营养只有每 100g 一个口径；② 身份只认显式链接；③ 餐记录只存快照；④ 来源与证据永远可见。

## 5. 记忆系统（完整功能清单）

**数据**：`ai_memories` + 新增列 `importance`、`lastUsedAt`、`useCount`、`supersededById`、`expiresAt`、
`sourceMessageId`、`linkedEntityType`、`linkedEntityId`、`relatedIds`（一跳关系，可选）。
容量：**软顶 2000 / 硬顶 5000**；单条 140 字。

**捕获（五条路）**
1. 对话命令 `memory.remember` / `memory.forget`（信封 → 确认 → 写）。
2. 记忆页手写。
3. 「提炼记忆」按钮（候选点选才写）。
4. 会话结束自动提炼（D6：进待确认队列）。
5. **会话级临时记忆**（G20）：只在这次对话生效，不落库（如「我在出差，只有便利店」）。

**治理**
- 写入：嵌入 + cosine 判重（≥0.96 拒绝 / 0.88–0.96 提议合并 / 否则新增）；敏感红线；否定极性检测（提议替换）。
- 改口：`supersededById` 留痕，检索只看 active；页面可看历史、可撤销（G2）。
- 过期：`kind=context` 可带 `expiresAt`（默认 30 天），到期**提议**归档。
- 整理：后台找近义簇（cosine≥0.9）与长期未用条目 → 「整理建议」，确认才动。
- 晋升（G1）：每条可「转为忌口/偏好」→ 走 `constraints.set`；提炼候选标「建议作为约束」。
- 实体链接（G19）：可关联 dishId/foodId/venueId，供检索与过滤 join。

**注入**
- query-aware：当前消息嵌入 + 关键词 + 标签 → RRF；**门控**（max cosine < 0.35 关闭语义路）；
  **MMR λ=0.7** 去冗余；排序 = 置顶 > 相关 > 重要性 > 近期；三档预算（D4）。
- 会话内快照（G17，学 Eta `ConversationMemoryPins`）：同一会话内记忆段**逐字节稳定**，只在记忆变更/
  压缩/换模型时重建 —— 为 provider 前缀缓存服务（见 §9）。
- D11：记录本轮注入的记忆 id，气泡「本轮参考了 N 条记忆」可展开。

**用户控制**：查看/编辑/置顶/删除/清空/复制；**导出 Markdown/JSON + 粘贴导入**（G4，逐条确认，带版本与上限校验）；
注入开关；分页 + 搜索（G5，2000 条不卡）。

## 6. 检索系统（S12 v2，完整）

- **嵌入**：`bge-small-zh-v1.5` int8（512 维，≈24MB，MIT），随包 + 首帧空闲预热；Dart WordPiece（maxLen 64，
  前缀策略 A/B）；长驻 worker isolate；int8 vs fp32 实测选型；失败降级关键词+标签（如实提示）。
- **索引**：Drift 表 `embedding_index(ownerType, ownerId, modelId, dim, encoding, textHash, vector, updatedAt)`；
  记忆 f32 / 菜品与食物 i8 / 超大规模 b1；**ownerType 覆盖 memory / menuItem / dish / food** 四类。
  规模三档：≤5 万 int8 暴力；>5 万 b1 预筛 + int8 重排；>50 万 HNSW。
- **一致性**：同事务或异步补齐 + 启动 orphan sweep；`textHash` 跳过未变；换模型全量重建；**不进备份**（D7）。
- **查询管线**：硬过滤（过敏/饮食标签/营业/今日菜单/状态）→ 向量 topK 200 + 中文 bigram 关键词 + 标签 →
  **RRF**（`Σ 1/(60+rank)`）→ boost（置顶/重要性/口味/近期）→ **MMR** → 截断（搜索 50 / AI 短名单 30 / 注入按档）。
- **查询理解**：同义词/别名表（清淡/辣/面/汤、土豆↔洋芋…）+ 槽位（餐次/地点/窗口/忌口/营养意图），
  不额外调 LLM。
- **可观测（G13+G21）**：调试面板显示 关键词/阈值/各路命中数/候选分数；「搜索模拟」可切
  `BALANCED / KEYWORD_FIRST / SEMANTIC_FIRST`（学 Operit 的 scoreMode）看结果差异。
- **评测（P0 门槛）**：≥100 条中文口语查询 + hard negatives；recall@10 / nDCG@10 / MRR；
  混合 vs「关键词+标签」相对提升 ≥20% 才上线；golden 向量夹具防模型接错（G12）。

## 7. 食物/菜品系统（S13，完整）

**四层职责**：食物库=每 100g 事实；食堂菜=供应事实；菜品库=份量模板；餐记录=不可变快照。

**字段增量（schema 28，纯加法）**
- `dish_library`：`servingGrams`、`nutritionBasis`、`basisAssumed`、`sourceType`、`sourceId`、
  `sourceUpdatedAt`、`userEdited`。
- `menu_items`：`servingGrams`、`tagsJson`（烹饪/口味/餐次）、`ingredientsJson`（食材 + 来源 + 置信度）。
- `meal_items`：`sourceType`、`sourceId`。
- 回填：菜品库 `perServing/100g/basisAssumed=1`；餐记录按 `foodId` 推断来源。

**配料与过敏原（D5 / D9）**：用户 > AI > 词典 三层来源；AI 与营养分析**合并成一次「菜品分析」调用**；
**过敏原由食材推导**（蛋→蛋类、面粉→麸质、虾蟹→甲壳类、豆腐→大豆…）；过滤用
「忌口词 ∩（食材 ∪ 别名 ∪ 过敏原组）」；徽标「已确认 / AI 推断 / 关键词推测」；没数据不假装安全。
**纠正**：`foods` 无 `allergens_json`（schema 22 已删）⇒ 食物库提供不了配料；本方案落成后
计划 solver 的 `allergen_conflict` 才第一次拿回食物侧输入源。

**写入路径矩阵**（全部落到 `MealRepository.create`）
| 动作 | 默认份量 | 营养 |
|---|---|---|
| 食堂菜加入午餐 | `servingGrams ?? 100` | per100g × 克数（标「按 100g 估算」） |
| 食堂菜存为菜品 | 同上 | per100g 存库，展示按份算（`每份 = per100g × servingGrams/100`） |
| 食物库记录食用 | `defaultServingGrams ?? 100` | per100g × 克数 |
| 菜品库加入餐 | `dish.servingGrams ?? 100` | 每份值 × `grams/servingGrams`（不再乘 100g） |
| 拍照识别 | 识别克数 | 命中食物用其值，否则估算并标来源 |
| AI 对话 | 按命中来源 | 同上，来源写 `sourceType/sourceId` |

**建菜时的食物库匹配（R8）**：建完跑本地匹配（精确名 → 别名 → 归一化 → 可选向量），命中给三选一：
「引用食物库营养」（默认，精确同名且可靠）/「AI 重新分析」/「先不填」；引用写
`origin='food_library'` + 链接 `confirmed`。不静默填。

**AI 路由**：今日食堂有 → 食堂菜；否则菜品库；否则食物库；都没有 → 提议 `food.create`；
`canteen.dish.create` / `canteen.dish.nutrition` 增加可选 `nutritionFrom: 'food'|'ai'|'none'`（旧行为不变）。

**同步与陈旧**：食堂重分析 → 菜品库提示「食堂营养有更新」，用户点同步；`userEdited` 只提示不覆盖；
**餐记录永不同步**。来源删除 → 链接悬空显示「来源已删除」，不级联删菜品。

**无 AI 可用（D10）**：食堂菜可手动填每 100g（`origin='user_input'`）；配料可用词典/手填；
检索退关键词；记忆退置顶+重要性——全链路无 AI 也能用。

## 9. 性能与响应速度专项（G17/G18 等）

> 现状事实：上游 TTFB ≈11s、整请求 40–46s（供应商侧），App 侧能优化的是「少发 token、少阻塞、少等待」。

1. **请求前缀稳定化（最大收益）**：消息布局改为
   `[固定提示][协议+约束+会话记忆快照（会话内不变）][历史（追加式）][动态快照][本次用户消息]`，
   目标是命中 provider 的**前缀缓存**（缓存命中时上游处理更快）。
   逐协议确认中段 system 消息兼容性；`anthropicMessages`/`responses` 用其 `system` 字段 + 显式 cache breakpoint。
   会话记忆快照按 Eta `ConversationMemoryPins` 思路实现（会话内逐字节稳定，变更/压缩/换模型才重建）。
2. **快照装配**：分段 `Future.wait` 并发；用 Drift 变更流做**失效信号**，未变段直接复用上次字符串；
   消 N+1（食堂三级查询合并成一条 join/一次性拉取）。目标：装配 <10ms。
3. **记忆排序**：端上嵌入 <15ms；相关性全低直接跳过语义路（省 10ms+）。
4. **检索**：索引常驻内存、早退、id 过滤下推；1 万条 <10ms、搜索 p95 <50ms。
5. **网络**：连接复用（keep-alive）、流式首字优先、超时预算维持（connect 10s / send 30s / receive 120s / total 4min）。
6. **写放大**：`lastUsedAt/useCount`、索引更新都节流批量提交（≥10 分钟或会话结束）。
7. **启动**：首帧后空闲预热模型；索引后台构建（**充电 + 空闲**才跑，可暂停、断点续跑，G11）；
   首屏 0 阻塞。
8. **量化目标**：App 侧每轮额外开销 <50ms；搜索 p95 <50ms；1000 菜索引 <15s；常驻内存 <40MB。
