## 1. 评估结论（基于设备截图 01–23 与代码核对）

| 编号 | 问题 | 根源 | 定性 |
|---|---|---|---|
| P1 | 我的·健康数据三卡：中间卡字号观感与高度和两侧不一致（用户点名） | 实现把「kcal/天」塞进值文本 → 窄卡折行 → 卡片随内容变高；**设计稿的值就是纯数字**（`1,480`），单位从不进值行 | 实现偏离设计稿 + 等高语义缺失 |
| P2 | 我的·成就四格高低不齐（用户点名） | HTML 的 CSS grid 行内项目**天然等高**；Flutter `Row+Expanded` 各自取内容高度，上轮去 maxLines 后第一格三行更明显 | 设计稿语义未带到 Flutter |
| P3 | 四处浅色 hero（饮食记录/今日菜单/今日 AI 入口卡/我的身份卡）白字在渐变淡端几乎不可读（实测对比最低约 1.1:1） | 设计稿自身缺陷：渐变淡到 `#ECFBF5` 却规定 `text-white` | 用户指示覆盖：配色不得影响文字显示 |
| P4 | 饮食页「近 7 日趋势」空态是一大片 120dp 空白 + 无意义的星期标签行 | 空态是 App 自设计面（设计稿只有有数据形态），当前实现把「有数据」的高度原样用在「无数据」 | 空态未设计 |
| P5 | 同一概念两套规格：设置页健康数据（居中白卡）与今日页本周趋势（左对齐灰块带迷你曲线） | 设计稿本身就是两个模式（stat tile vs trend tile）——**保留两种，但各自内部规格必须一致** | 不是缺陷，是边界澄清 |

## 2. 修复设计

### R1 统计瓦片（对应 P1/P2）
- 新共享组件 `LfStatTile`（design widgets）：值行 = 大数字（`LfText.headline`
  w800 primary）+ 可选小单位（`LfText.micro` muted，同行不折行，
  `FittedBox.scaleDown` 兜底）；标签行 = `LfText.micro` muted 居中，
  `height: 1.25`（设计稿 `leading-tight`）。成就变体：图标圆 36dp 在值位。
- 组容器：`IntrinsicHeight` + `CrossAxisAlignment.stretch`，把 CSS grid
  「行内等高」语义带到 Flutter；组内间距 `gap-2`（8dp，与设计稿一致）。
- 健康数据值回归设计稿：BMI `22.3`、BMR `1,424` + 小单位 `kcal/天`、
  水分 `2.0L`。单位小一号且 muted —— 数值获得强调，卡片等高。
- 成就：四格等高，标签完整不省略（沿用上轮修复），行高 1.25 收紧。

### R2 hero 文字可读性（对应 P3）
- 规则：**浅色渐变上用墨色文字**。主文字 `c.foreground`，次级
  `c.foreground.withValues(alpha: 0.7)`，弱线/图标 `alpha 0.2–0.6`。
  亮色主题墨字对 mint 渐变实测对比 7.8:1（最深端）～15:1（最淡端）；
  暗色主题 hero 渐变本就是深绿→墨黑，`c.foreground` 在暗主题下是浅色，
  对比 5.8:1+ —— **同一规则亮暗两态自动成立**，不需要新 token。
- 改动面：`HeroSection` 默认文字色、饮食记录 hero、今日菜单 hero、
  今日 AI 入口卡、我的身份卡。训练页暗 hero 白字对比已达标，不动。

### R3 空态紧凑（对应 P4）
- 趋势卡空态：图区 120→72dp，隐藏星期标签行（空图表的坐标轴是装饰）；
  有数据形态保持 120dp + 标签，与设计稿一致。

### R4 明确保留（对应 P5）
- 今日页趋势瓦片（灰底、左对齐、迷你曲线、升降色）是设计稿的独立模式，
  不与统计瓦片合并；其单位规则（`69.4` 大 + `kg` 小）与健康数据瓦片一致，
  两处共同构成「数字强调、单位弱化」的全 App 语言。

## 6. 第四轮：并排判据缺陷（2026-10-03，用户报告「今日热量卡片不一样」）

### R6 缺陷与根因

用户在 360dp 机型上截图显示：热量卡的圆环被挪到宏量条**上方**并居中，与设计稿
（圆环在左 / 宏量条在右）不符。

根因 = 三处 `constraints.maxWidth < 300` 常量判据：360dp 手机页面左右各 16dp、
卡片内边距各 16dp ⇒ 热量卡内宽 = 360 − 32 − 32 = **296dp**，恰好 `< 300` 成立，
于是主流手机一律走竖排降级分支。同一常量还误伤体重趋势三格与饮水/步数两格。

设计稿（`ui设计/pages/今日.html`）**没有任何断点**：无头渲染 430/376/360/320px
四宽全为并排（`tmp/cal-stack.png`）；320px 下设计稿**自身裁字**（`156 / 200 g`
被裁、饮水/步数第二格被裁，`tmp/cal-320-2x.png`、`tmp/qs-320-2x.png`），
说明 320px 不是设计支持的宽度，退化时机只能由实现决定。

### R7 判据替换

新增 `lib/app/design/widgets/text_fit.dart`：

- `fitsRow(context, available, baseNeed)` ＝ `available >= baseNeed × bodyTextScale`；
- `bodyTextScale` 取 12px 处的系统字号比值（Android 非线性字号下 `scale(1)` 不准）；
- `LfRowBudgets` 存三个纯算术预算，按各调用点**实际可见宽度**取值：

| 卡片 | 可见宽度 = 视口 − | 360dp | 320dp | 预算 |
|---|---|---|---|---|
| 热量卡 / 趋势三格（卡内） | 64 | 296 | 256 | 290 |
| 饮水 / 步数两格（页面级） | 32 | 328 | 288 | 300 |

- **不用 `TextPainter` 实测**：flutter_test 的 Ahem 字体每字符按一个全角字宽上报，
  实测值约为真机 Roboto 的两倍，会把「1.0× 下放得下」判成放不下（该实现曾一度
  引入并因此红了 360dp 用例，已撤）。

### R8 一并修正

- **占比行形态**：按设计稿 CSS `flex items-center gap-3` 还原为行内三片段（放得下
  一行；列窄时各片段内部折成「名称 / 百分比」两行——用户截图 JPG 即此态），
  取代原先的固定三列两行。
- **右列对齐**：`macros` Column 默认 center 导致占比行/空态跑到中间，补
  `crossAxisAlignment: start`，实测三条宏量标签与占比行左缘 182.7 / 183.3dp。
- **2.0× 溢出**：`MacroBar` 数值串与 `meal_timeline` 元信息串在 320dp + 2.0× 下
  溢出（0.5px / 150px，夹具加数据后才暴露），改用 `Flexible` + `FittedBox.scaleDown`。

### R9 验证

- 新增 `test/features/dashboard/dashboard_breakpoint_test.dart` 4 例：360dp 三卡并排
  （用户机型）、右列左对齐、320dp 竖排、320dp+2.0× 竖排不溢出。
- **隔离变异**：把 `fitsRow` 改回 `available >= 300` 两次，均只有 360dp 用例转红
  （320dp 两例保持绿）⇒ 断言具体、非过宽。
- 门禁 **EXIT=0（1700 passed / 3 skipped，format 0 changed，analyze clean）**。
- 设备：emulator-5556 设 `wm density 480`（1080px ⇒ 恰好 360dp）复现并复验；
  截图 70（修前竖排）/ 71（修后并排）/ 72–73（趋势三格、饮水步数两格并排）/
  74（右列对齐修正后）。实测宏量条左缘 168.0dp > 圆环右缘 148.7dp；
  饮水/步数两卡 16.0–173.7 / 186.0–343.7dp（间隙 12.3dp ≈ 设计 `gap-3`）。

## 7. 第五轮：饮食界面表现重设计（2026-10-03，用户点名三条）

用户原话（三条一并交付，详见 `docs/evidence/2026-10-03-nutrition-presentation-redesign.md`）：

1. 「饮食界面的五个菜单按钮能不能移动到顶部，不然每个界面的位置都不在一个地方」
2. 「食物添加界面的弹窗卡片太丑了，你根据现在的主题，重新设计」
3. 「食物库的界面也很丑，食物卡片的表现形式不直观」

### R10 需求①：胶囊行统一 —— **对前几轮的显式偏离**

- 旧实现三处各渲染一条（记录页夹在 hero 与趋势卡之间 / 菜单页在 hero 之下 / 未画 tab
  在外壳里），实测三个高度（y≈300 / 139 / 60）。
- 现为 `NutritionPage` 页头**唯一实例**，贴状态栏下缘，各 tab 页头紧接其下；记录页趋势卡
  让位到胶囊之下。
- **偏离 §R2 / 前轮的「hero 必须铺到屏幕物理顶边」**：记录与菜单 hero 改
  `respectTopInset: false`、不再贴物理顶边。用户仲裁优先于保真（用户要的是「五个按钮
  在同一位置」，hero 贴边与之不可兼得）。
- 旧整 App 级契约 `expectBleedingHero` 删除；覆盖面由三处保留：组件级「渐变必须铺到物理
  顶边」、训练页内联 hero 断言、新 `expectStickySubTabChips`（行底色贴顶 `top == 0`、
  行高 = 54 + 叠层、内容/页头随叠层整体下移且不入状态栏带）。
- 代价（如实记录）：记录页空态文字在滚动位置 0 时更靠下，设备走查确认**不是遮挡缺陷**
  ——滑到底后底栏之上无内容节点（`navReserve` 生效，截图 86）。

### R11 需求③：食物卡以「热量」为视觉主指标

图标块（`FoodCategoryIcon` 44dp）+ 名称（单行省略）+ 宏量三色点（6×6，语义色
`protein/carbs/fat`）+ **右端 `NNN kcal`（15px）与「每 100g」（10px）**+ 来源徽标；缺热量
写「—」+「无热量数据」且**不写 0**；营养不完整另有文字提示（不只靠颜色）。两条数据路径
（目录 controller / 仓库直搜）共用同一件搜索框、同一张卡、同一套空态骨架 ⇒ 用户看到的
食物卡不再因数据来源变样；`FoodSearchTab` 不再渲染 `ListTile`。

### R12 需求②：记录一餐弹层（主题内重做）

四枚餐次胶囊（替代下拉菜单，选中主色实心，≥44dp + 语义 `button/selected`）+ 主题搜索框
（替代 M3 `SearchBar`）+ 定高结果列表 + 「已添加 N 项」条目卡（克数 `AppNumberField` +
按当前克数换算的热量/宏量）+ 备注（可选）+ **合计卡（kcal 大字 + 三色点）**；正文整体可滚
（`SingleChildScrollView` + `maxHeight 620`），按钮 `OverflowBar` 常驻；错误文案内联在按钮
上方。搜索 future 只在查询变化时重建（改克数不再闪回加载态）。

**空查询不预留定高结果区** —— 这一条由设备走查发现：定高 168dp 在 360×780dp 上留出大块
空白并把「合计」卡挤出可视区；改零高内联提示后合计卡完整可见（已补几何断言 + 变异 M10）。
